# 運用コンソール（ライブオペレーション）手順書

`tools/ops-console/` は管理API（`/v1/admin/*`、`server/src/http/admin.ts`）だけを呼ぶ静的なシングルページアプリです（フレームワーク・実行時の依存なし。ビルドはオフラインで動きます）。権限・上限・監査はすべてサーバー側で判定され、コンソールの表示（ボタンを隠すなど）は補助にすぎません。

## 1. 準備とデプロイ

| 手順 | 内容 |
|---|---|
| トークン | 担当者ごとに `ADMIN_TOKENS` に `{"name":"<担当者名>","role":"viewer\|operator\|admin","sha256":"…"}` を追加（`docs/ops/deploy.md`）。**2人ルールのため、admin は必ず個人ごとの名前付きトークン**にする（旧 `ADMIN_TOKEN` は全員が `legacy` になり、承認者と依頼者を区別できない） |
| ビルド | `cd tools/ops-console && OPS_API_BASE=https://api.example.com OPS_ENV_LABEL=production node build.mjs` → `dist/` |
| 置き場所 | `dist/` を任意の静的ホスティング（Cloudflare Pages など）に置き、**Cloudflare Access で社員だけに限定**する。ホスト側で `Content-Security-Policy: frame-ancestors 'none'`・`X-Frame-Options: DENY` を返す（`serve.mjs` と同じ） |
| CORS | Worker の変数 `ADMIN_CONSOLE_ORIGINS` にコンソールのオリジン（`https://ops.example.com`）を入れる。複数はカンマ区切り。ワイルドカード・パス付きは無視される |
| ローカル | `cd server && npx wrangler dev --var ADMIN_CONSOLE_ORIGINS:http://127.0.0.1:9217 …`、`cd tools/ops-console && OPS_API_BASE=http://127.0.0.1:8787 node build.mjs && node serve.mjs 9217` |

`OPS_ENV_LABEL` はヘッダーのバッジ（production は赤）。本番と staging でビルドを分け、取り違えを防ぎます。

## 2. セキュリティの考え方

- **認証**：すべての呼び出しに `Authorization: Bearer <トークン>`。トークンはそのタブの `sessionStorage` にだけ保存（タブを閉じると消える）、URL・Cookie・localStorage には入れない。401 を受けたら自動でログアウト。
- **権限**：viewer（閲覧・検証・ドライラン）＜ operator（版の登録、補填の依頼・却下、大会の作成・中止、隔離の解除）＜ admin（有効化・ロールバック・予約の取り消し、補填の承認、BAN／解除）。足りなければ 403。
- **監査**：閲覧も含め全呼び出しが監査ログ（誰が・権限・操作・対象・理由・変更前・変更後・成否・時刻）に残る。書き込みはコンソールの確認ダイアログで理由（3〜500文字）を必ず入力する。失敗・権限不足も残る。
- **CSRF**：Cookie を使わないので、他サイトがログイン状態を悪用できない。加えて、書き込みは `content-type: application/json` 必須（必ず CORS のプリフライトが走る）、許可していないオリジンからの呼び出しはトークンが正しくても 403、資格情報付きの CORS は許可しない。
- **XSS**：サーバーのデータ（プレイヤー名・メモなど）はすべてテキストとして描画（`innerHTML` を使わない）。CSP は `script-src 'self'`・`style-src 'self'`・`connect-src 'self' <API>` で、インラインのスクリプト・スタイルは動かない。
- **秘密情報**：リポジトリにトークンはない。e2e は実行ごとにランダムなトークンを作り、サーバーにはその SHA-256 だけを渡す。

## 3. 画面ごとの手順

### リモート設定（REQ-OPS-002〜009）
1. **下書きの検証**：バンドル（部分）JSON を貼り「検証（ドライラン）」。サーバーで起動時と同じ検証器が動き、問題が「ゲーム日の切り替え／アセットカタログ／ガチャ／ルールセット／その他」に分かれて出る。何も保存しない。
2. **版として登録**（operator）：検証が通ったものだけ登録できる。同じ内容は既存の版が返る。
3. **比較**：比較元・比較先（`base` は出荷時のマスター）を選び「比較」。パスごとの変更前・変更後。バナーやイベントは `id` で突き合わせる。
4. **有効化**（admin）：「有効化…」を押すと、まずドライラン（`POST /v1/admin/config/dry-run`）が走る。問題があれば赤い一覧が出て**確認ダイアログは開かない**。予約は「有効化の予約時刻（JST）」に入力。「事前チェック」はドライランだけ。
5. **ロールバック・予約の取り消し**（admin）：同じくドライラン→確認。ゲーム日の切り替え（REQ-DAY-002：1時間の猶予・過去48時間の書き換え禁止）は、取り消しやロールバックで後ろの予約の「前の版」が変わる場合も検査される（「pending activation … would become invalid」）。
6. 反映は最大30秒。プレイヤー側の `GET /v1/config` の `versionId` で確認する。

### ガチャ カレンダー（REQ-OPS-027）
- 版（active／base／任意の版）を選ぶと、その版のマスターでバナーをタイムラインに描く（赤い縦線が現在、点線が予告期間、斜線が常設、下線が有償のみ）。日付はゲーム日（`progression.dayRollover`）。
- 表：期間（開始・最終のゲーム日）、ステップアップの各段の価格（枠付き＝10枠目の専用表あり）、天井。
- 天井グループ：締め日と引き継ぎの連鎖（例 `pickup_ginga → standard`）、プレイヤーに表示される引き継ぎの文言。
- 「提供割合」で、**プレイヤー向けと同じ関数**で作った提供割合ページを表示（公開前・終了後のバナーも）。新しいバナーは登録後・有効化前にここで必ず確認する。

### イベント・大会
- イベントの状態と期間、大会の一覧（受付・開始・参加人数）。
- **ミニ大会を作る**（operator）：初期値は「今から受付・1時間後に締め・その5分後に開始・1組4人・8頭立て」。作成後は詳細と中止（表彰前のみ、賞品なし）。

### メンテナンス（REQ-MNT-011、contracts/protocol.md §46.6、Round 17）
- 予定・実施中の窓（状態・開始・終了・お知らせ開始・範囲・メッセージ）。実施中は「今すぐ終える」、始まる前は「取り消す」（admin）。
- **新しいメンテナンス**：ID・開始・終了（日本時間）・お知らせ開始（空欄＝24時間前）・範囲（すべて／グループ）・日本語と英語のメッセージ。「プレビュー」でサーバーの検査結果と、プレイヤーに見えるお知らせ帯を日英で表示（何も保存しない）。「予定する」は admin、理由必須。窓は重ねられない。
- **対応バージョン**：iOS／Android の最低・推奨とストア URL（App Store／Google Play の https だけ）、最低のエンジン水準。最低を上げるのは新しいアプリの配信が始まってから。
- どの変更も、有効な版から `maintenance` だけを置き換えた版として今すぐ有効になり（30秒以内に反映）、監査ログに `maintenance.schedule`／`maintenance.cancel`／`maintenance.versions` で残る。他の版の有効化が予約中なら 409。
- 購入レシート・ストア通知・退会・進行中のレースの確定はどの窓でも止まらない。デプロイとの関係は docs/ops/deploy.md §7.2。
- 予定するときに確認すること：cron とオブジェクトのアラーム（イベント・大会の締め、シーズンの切り替え、週の締め）は窓の中でも動くので、**締めの直前に窓を置かない**（参加できないまま締まる）。窓がゲーム日（`progression.dayRollover`）をまるごと覆うと、その日のログインボーナスやデイリーが受け取れない。どちらも避けられない時はお詫びの補填で埋める。待ち行列にいた人でレースが組まれた場合は、来なかった人を CPU が引き継いでレースは確定する。
- 2人が同時に変更すると、後の人は 409（「有効な設定が変わった」）になる。読み込み直してからやり直す。

### プレイヤー サポート（REQ-OPS-020〜026・033）
1. 検索欄にプレイヤーID、または招待コード（`XXXX-XXXX`、小文字・ハイフンなしも可）。
2. 財布：有償／無償／返金負債／有償残高の円換算／今月の支払い／年齢帯、有償ロット。購入履歴（返金・上限超過・sandbox）。
3. サポート用の印：種類ごと（広告 `ads_anomaly`、招待の不正 `invite_*`、購入 `promotion_not_reached`・`once_duplicate`・`pass_duplicate`・`purchase_while_*` など）。
4. アカウント削除：状態・削除予定・済んだ手順（確認トークンは表示されない）。「削除済み」はデータが消去された墓標のあるID。
5. **補填**（operator）：無償コインとアイテムだけ（有償コインは作れない）。1万コイン・1アイテム100個以下は即付与。超えると「承認待ち」になり、**依頼者以外の admin** が「補填の承認」画面で承認したときに付与される（上限10万コイン・1000個、72時間で期限切れ）。台帳の理由に依頼者と承認者が残る。
   - **Round 12（REQ-BOX-010）**：補填・個別配布・一括配布は**プレイヤーのプレゼントボックスに入る**（財布はプレイヤーが受け取った時に変わる）。表示（お詫びの品／メンテナンスのお詫び／不具合のお詫び／運営からの贈り物）と受け取り期限（空欄＝補填90日・配布30日、「期限なし」も可）を選べる。プレイヤー画面の「プレゼントボックス」に未受け取りと履歴（内部のメモ付き）が出る。2人承認と24時間の上限は入れた時点で数える。削除済みのアカウントには入れられない（404）。
6. **BAN／解除**（admin）・**隔離の解除**（operator）：理由必須。BAN は期限（JST）か無期限。

### 補填の承認（REQ-OPS-026）
- 状態で絞り込み（既定は承認待ち）。自分が依頼したものは承認ボタンが押せない（サーバーも 403）。
- 付与に失敗した（`支払い失敗`）承認済みの依頼は「支払いを再試行」で再実行できる（プレイヤー側で冪等なので二重にならない）。

### 監査ログ
- 操作者・対象（`player:<id>`、`config:<版>`、`tournament:<id>`）・操作（`compensation.approve` など）で絞り込み。行の「前／後」で変更前・変更後の値。

### KPI
- `docs/ops/kpi-queries.md` のクエリをビルド時に取り込み、見出しごとに表示（SQL のコピー、ドキュメントへのリンク）。実行は Analytics Engine の SQL API（Account Analytics:Read のトークン。コンソールは保持しない）。

## 4. よくある対応

| 状況 | 手順 |
|---|---|
| 障害のお詫び（全員） | 一括配布 `POST /v1/admin/grants/bulk`（1人あたり1万コインまで、API から） |
| 個別の大口補填 | 補填を依頼 → 別の admin に承認を依頼（Slack 等で依頼IDを共有） |
| 設定を戻したい | リモート設定 →「1つ前にロールバック」（ドライランの結果を確認） |
| ゲーム日の切り替えを変える | `progression.dayRollover` を変える版は、効果の1時間以上前に有効化し、`previousHourJst` は今の時刻のまま（ドライランが具体的な理由を出す） |
| 止める必要のあるデプロイ | メンテナンスで窓を予定 → 窓の中で「検証サーバー → Worker」→ 窓を今すぐ終える → 必要なら補填（「メンテナンスのお詫び」）（deploy.md §7.2） |
| 古いアプリを止める | メンテナンス → 対応バージョンの最低を上げる（新しいアプリの配信が始まってから） |
| 招待の不正の疑い | プレイヤー サポートで `invite_*` の印と招待した人の一覧を確認 → 必要なら BAN |

## 5. テスト

- サーバー：`cd server && npm test`（`test/ops-console-api.test.ts`：CORS、ドライラン、差分、カレンダー、招待コード検索、2人ルール）。
- コンソール：`cd tools/ops-console && npm test`（KPI の取り込み）。
- e2e：`scripts/console-e2e.sh`（`SERVER_PORT=9117`、`CONSOLE_PORT=9217`、`VERIFIER_PORT=9017`）。wrangler dev を新しいローカル状態で起動し、Playwright（headless Chromium）でログイン拒否・viewer の読み取り専用・CORS/CSRF・下書きの検証・版の登録・招待コード検索・補填（即時と承認待ち）・ミニ大会・承認（自己承認の拒否）・ドライランでのゲーム日の問題・有効化・差分・カレンダーと提供割合の一致・BAN／解除・監査ログ・KPI を確認。スクリーンショットは `tools/ops-console/e2e-screenshots/`。

## プレイヤーの履歴（REQ-HIST-010、contracts/protocol.md §33.4）

プレイヤー画面の「履歴（本人の画面と同じ・読み取り専用）」：種類（購入／有償コイン／無償コイン／ガチャ）を選んで「表示」、20件ずつ。本人の画面と同じ行に、サポート用の内部の値（購入の取引ID、台帳の理由文）を足して出す。プレイヤーがアプリの「問い合わせ」で作った下書きの番号（`P-…`・`C-…`・`G-…`）は「番号で開く」でその行を開ける（期間外・他人の番号は「見つかりません」）。API は `GET /v1/admin/players/:playerId/history?kind=…`／`?refs=…`（viewer、読み取りのみ、監査ログの action は `player.history.view`）。削除済みアカウントは 404：匿名で保存された法定の記録はここからは見えない。
