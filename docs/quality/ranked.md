# ランク戦のバランスとマッチング（ranked）— 品質パス2

品質パス2の3本のうち「ランク戦」。品質パス1の終わりに、台本で上手く乗るプレイヤー（スクラッチパッドの WinDemo）が相棒でランク戦に約50回出て**1度も勝てなかった**（最高3着）。初心者マッチは20戦で8勝ほど。勝てないランク戦には人は戻らず、お金も払わない。

ここでは**サーバーが実際に作るランク戦の場**を、乗り方の違う3人で数千レース走らせて原因を数字で確かめ、場の作り方（サーバーの設定）で直した。エンジン・ルールセットは1つも変えていない（ゴールデンは動かない）。

- ブランチ：`quality/ranked`
- 触ったところ：サーバー（ランク戦の場の作り方 `rankedField.ts`・`orchestrate.ts`・`raceConfig.ts`、`progression.rankedField`、`beginnerMatch`）、検証のハーネス（`Muchi.Verifier/RankedHarness.cs`）、クライアント SDK（`RankedFieldCheck`）、Unity のゲーム層（`RaceResultModel.FieldLine`）、プロトタイプの結果画面と見本のランク戦。

## 0. 結論

1. **一番の原因は「コースが馬を見ていない」こと。** ランク戦のコースは8コースから無作為で、相棒（芝 1600〜2400m）にとって**約半分（160戦中 71〜89戦）が適性外**（ダート3コースと1200m）。適性外は最高速とスタミナが −5% ずつで、上手い人でもほぼ勝てない（C級・相棒：適性内 43% 勝ち、適性外 8%）。
2. **初心者マッチの後に崖がある。** 5戦目までは平均的な人で 52% 勝ち・3着以内 79%、6戦目から 7%・17% に一気に落ちる（CPU が レベル1・78% → レベル3・100% に一度で戻る）。
3. **クラスが上がると場が弱くなっていた。** CPU の馬はクラスの上限まで「下げる」だけだったので、B級より上では場の半分（R の馬、合計 2,700〜2,900）が上限よりずっと下。育てた馬には C級より A級・S級の方が楽で、クラスの階段に意味が無かった。
4. **直したこと**（`progression.rankedField`、リモート設定で変えられる）：① コースは馬の適性に合うものから選ぶ ② CPU の強さ（レベルと能力合計）をクラスで決める（C 2,800・L2〜3／B 3,200・L4／A 3,500・L4／S 3,600・L4〜5）③ 初心者マッチの後は CPU を 5戦かけて元の強さに戻す（ramp）④ 初心者マッチの CPU を 780‰ → 860‰（コースが合うようになって楽すぎたので R10 の帯に戻した）。
5. **結果**：上手い人＋育てた馬（30日目）の勝率は全クラスで 1/6 以上（C 52〜55%、B 35〜39%、A 34〜36%、S 32〜34%）、平均的な人の3着以内は 31〜41%、連打だけの人はどこでも勝てない（0〜7%）。6〜15戦目の平均的な人の3着以内は 17% → 46%（崖が無くなった）。
6. **負けた理由が読める**：ランク戦で負けた時、結果画面の「振り返り」の行の先頭に「能力の差：相棒 3320 ／ この場のCPU 3600。調教で伸ばすと勝ちやすい」か「能力は互角以上（…）：差は乗り方」が出る（新しいシートは作らない。続く行は品質パス1の敗因と仕掛けの振り返り）。
7. **経済**：E1〜E20 のシミュレーションは場所を一様に引くので値は変わらない（E1 64.2）。ただし**ハーネスが測った平均的な人の着順で E1 を出すと、変更前から 73.1（目標 40〜65 を超える）**、変更後 76.4。シミュレーションの「平均的な人＝一様な着順」という仮定は、もともと実際の場と合っていなかった。E1 をこの数字で見直すかはオーナーの判断（§6）。

## 1. 測り方

### 1.1 ハーネス

- **場はサーバーが作るとおり**：`server/src/domain/rankedSample.ts` が、待ち行列に1人で並んだプレイヤーを `MatchmakerCore` が CPU で埋め、`rankedMatchRules` → `createRace` → `buildRaceConfig` で作ったレース設定をそのまま集める（クラスの上限、コースの抽選、その日の馬場、CPU のスキル）。9組 × 160レース を `contracts/ranked-fields.sample.json` に（馬・コース・net は1回だけ書き、レースは鍵で参照。展開すると元の設定と完全に同じことをサーバーのテストが確かめる。古くなるとテストが落ちる：`npm run gen:ranked-sample`）。
- **乗り手は3人**（`engine/Muchi.Verifier/RankedHarness.cs`）：
  - 連打する人 `MasherRider`：ゲートから0〜12tick遅れて出る。手綱も内外も触らない。残り800mからムチのボタンを3〜8tickごとに連打（押して次のtickで離す）。
  - 平均的な人 `CasualRider`（品質パス1までの「初心者」）：半分は好スタートを逃す、手綱で脚を残さない、ムチは残り250〜600mのどこかから不規則に、掛かり・包まれには半分の確率で遅れて反応。1.4 では持つラインの −45%〜+25% で押し、溜めは0〜1秒。
  - 上手い人：1.3 は `SkilledRider`、1.4 は `TacticalRider`（品質パス1のハーネスと同じ）。
- 全員が**同じ場**を走る（比べやすい）。固定シードなので数字は毎回同じ。1.3（今のランク戦）と 1.4（切り替え後）の両方。
- `dotnet run -c Release --project engine/Muchi.Verifier -- harness-ranked "$PWD/contracts/ranked-fields.sample.json" [ルールセット]`

### 1.2 前提（オーナーが変えられる）

- **30日目の馬**：相棒を1か月毎日調教して SR の伸びしろ 240 を使い切り（ウッド／坂路／併せ馬の比で 速72・持48・瞬60・根36・気24）、覚醒1。素の合計 3,691。
- **クラスごとのレート**：C 1500・B 1550・A 1650・S 1800（クラスが上がるとレートも上がる想定）。レートは人間同士の対戦でしか動かないので、CPU との対戦が多いと実際は 1500 のまま。新しいクラスの帯（§3）がこの差を吸収する。
- 平均的な人は「始めたばかりの人」ではなく「手綱やムチの間合いを考えずに遊ぶ人」の代わり。

## 2. 監査：変更前

### 2.1 遊んでみた（新規・30日目相当）

プロトタイプ（`?demo=day7`）のランク戦を数本。1本目は青葉ダート1400：相棒は芝の馬なので、HUD もヒントも何も言わないまま、最後の直線で横並びから置いていかれた。敗因は「ムチが遅かった」。**負けた本当の理由（適性外のコース）はどこにも出ない**。出走登録の画面にもコースの適性は出ない（次に走るコースは抽選なので出しようがない）。

### 2.3 弱いところ（重い順）

| # | 弱いところ | なぜ楽しさ・継続・課金を損ねるか |
|---|---|---|
| 1 | **コースが馬の適性を見ていない**（ランク戦の約半分が適性外、−5%） | 腕を磨いても半分のレースは負けが決まっている。しかも理由が画面に出ないので「運が悪い」「ゲームが不公平」に見える |
| 2 | **初心者マッチの直後の崖**（3着以内 79% → 17%） | 一番離れやすい6戦目以降に、急に勝てなくなる。「最初だけ接待された」と感じる |
| 3 | **クラスが上がるほど CPU の場が弱い**（R の馬が上限よりずっと下） | 昇級に「強い相手と走る」重みが無い。C級が一番きつい（新規が一番長くいる場所） |
| 4 | **CPU の強さがレートだけで決まる**（人間と当たらないとレートが動かず、どのクラスもレベル3） | クラスの意味が上限だけ。上手い人が上に行っても相手の騎乗は変わらない |
| 5 | **負けの理由が「馬」か「乗り方」か分からない** | 調教すべきか、乗り方を変えるべきかが分からない。育成とランク戦がつながらない（品質パス1の育成の監査 F2 と同じ根） |

### 2.4 同じジャンルの強いゲームがうまくやっていること（一般論）

- **出走表は出る馬に合う**：レースは距離・馬場の条件で組まれ、出る馬はその条件に合う。合わない馬で走らされることは無い（あっても事前に分かる）。
- **新規の勝率はなだらかに下がる**：最初の数戦は勝たせ、その後は少しずつ普通の相手に（段差を作らない）。
- **階段を上がると相手が強くなる**：上のクラスは「より強い場」。育てた分だけ上で戦える。
- **負けの後に、次にすることが1つ出る**：育成か、乗り方か。

## 3. 変更（REQ-MM-009〜012、`progression.rankedField`）

すべてサーバーの場の作り方。エンジン・ルールセット・報酬の表は変えていない。

| | 中身 | 値 |
|---|---|---|
| REQ-MM-009 | **コースは馬に合わせる**：人間の馬のうち最も多くの距離・馬場の適性に入るコースから等確率（乱数は今までと同じ1回）。誰にも合わなければ全コースから | `courseFitsHorses: true` |

- **やめる時**：`rankedField` を消すか `courseFitsHorses: false` にすれば、次の試合から今までどおり（リモート設定、検証済み：`rankedFieldProblems`）。

### 3.3 経済（E1 を実際の着順で）

E1〜E20（`npm run economy`）は着順を一様に引くので、この変更で**値は1つも変わらない**（E1 64.2）。ただし「平均的な人＝一様」は実際の場では成り立っていなかった。ハーネスが測った平均的な人の着順（`contracts/ranked-places.vectors.json`：初心者マッチ・6〜15戦・各クラス、90戦目までは相棒そのまま、その後は30日目の馬）で無課金・毎日の人を90日走らせると：

| | E1（回/月） | E2（SSR/月） | 無償コイン/日 | 初勝利ボーナス/日 |
|---|---|---|---|---|
| 一様（今の E1） | 64.2 | 2.56 | 179.2 | 16.3 |
| 平均的な人・変更前の場 | **73.1** | 3.00 | 208.9 | 22.1 |
| 平均的な人・変更後の場 | **76.4** | 3.22 | 218.4 | 25.8 |

- 変更前から 40〜65 を超えていた（初心者マッチの 52% 勝ち、B・A級の弱い場）。この変更で +3.3回/月（C級で勝ちやすくなった分、B〜S級は少し下がった）。
- `server/test/economy.test.ts`（W8）がこの数字を 40〜77 で見張る（場か報酬の表が変わると動く）。

## 4. 負けた理由を読めるようにする

- `Muchi.Client.RankedFieldCheck`（レース設定だけから、決定的）：ランク戦で2着以下の時、相棒の能力合計（上限にそろえた後）と、この場の CPU の平均を比べる。98% 未満なら「能力の差：相棒 3320 ／ この場のCPU 3600。調教で伸ばすと勝ちやすい」、そうでなければ「能力は互角以上（相棒 2796 ／ この場 2800）：差は乗り方」。
- Unity：`RaceResultModel.FieldLine`（`FieldCheck`）。プロトタイプ：結果画面の「振り返り：」の行の先頭（続けて 1.4 の仕掛けの振り返りと会心の数、1行で折り返す）。初心者マッチでは出さない。新しいシート・画面は作っていない。
- 英語：`ui-en.json` に2文（`npm run l10n:missing` 0）。

## 5. 出し方

- サーバーの設定だけ（ルールセット・エンジンの水準は変わらない、検証サーバーも同じ）。Worker を出せば次の試合から。`rankedField` はリモート設定で戻せる（`rankedFieldProblems` が形と値を確かめる）。
- アプリ：結果画面の1行は新しいクライアント SDK から（古いアプリは出ないだけ）。

## 6. オーナーに決めてほしいこと

1. **E1 の基準**：今の E1（64.2）は「一様な着順」の仮定。実際の場の平均的な人では変更前 73.1・変更後 76.4。(a) このまま（仮定の E1 を目標にし続ける）、(b) 実際の着順の E1 を目標にして、ランク戦の着順コイン（`raceFreeCoinsByPlace.ranked`）か初勝利ボーナスを下げる（目安：65 に戻すには ランク戦の無償コイン −15% 前後）。勝ちやすくした分を「1勝の額」で返すのが普通のやり方。
2. **クラスの強さ**：C 2,800／B 3,200／A 3,500／S 3,600（と CPU のレベル帯）。S級は「育てた馬」の前提で相棒そのままでは勝てない（4%）。もっとなだらかにするなら S を下げる。
