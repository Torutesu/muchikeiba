目標：テストが落ちたら本物の不具合、通ったら本物の合格。負荷の高い共有マシン（4コアに load 15〜60）や日付（月末・週末・4:00 JST の切り替え）で落ちる「たまに落ちるテスト」を、**確かめている内容を弱めずに**原因から直す。製品の目標値（FTUE の aha 30 秒など）は変えない。

## 2. FTUE の時間（新しい測り方）

e2e の出力の例（負荷 10〜12、`E2E_ONLY=ftue`）：

```
 26.0 s   3 taps  aha①：差し切り（勝利画面）   (app clock 35.2 s − capture 7.7 − tap delivery 0.1 − render lag 0.0 − run-queue wait 1.4; noticed 0.1 s later)
119.7 s  14 taps  ホーム                       (app clock 147.7 s − capture 18.0 − tap delivery 0.5 − render lag 7.9 − run-queue wait 1.7; noticed 0.1 s later)
```

- 「app clock」はアプリが画面を出した時刻（テストの開始から）。そこから引くのは、テストの道具が足した分だけ：スクリーンショット（従来どおり）、タップの配達、レースの描画の遅れ（従来どおり）、run-queue 待ち。
- 静かなマシンの従来の 24.5 秒には、テストの道具の約 2 秒（ボタンの押せる確認と画面の検知）が入っていた。新しい測り方ではその分が入らないので、静かなときの数字は少し下がる。**目標 30 秒は製品の数字のまま**で、遅いアプリ（起動・画面の切り替え・レースの演出）はそのまま数字に出る。
- `E2E_ONLY=ftue` で FTUE だけ（タイトル → ホーム）を測れる。

## 5. オーナー／経済ストリームへの提案（今回はしていない）

- `economy.test.ts` を「通常」「イベント（E17）」「W8」の3ファイルに分けると、3つが別のワーカーで同時に走り、全体は一番長い1つ（27人分）で終わる。経済ストリーム（`quality/economy`）がこのファイルを同時に書き換えているので、衝突を避けて今回は分けていない。順番のクラスの `LONG_RUNNING` に新しいファイル名を足すだけでよい。
- 次に重いのはメモリのリポジトリの JSON の get / put（20日のプロファイルで 6 割）。読むだけの経路（`view` など）が読んだ状態を書き換えないことを確かめれば、さらに縮められる。
- dotnet test 全体（load 80〜100）：852 件すべて合格、1時間28分（AssetDelivery を含む）。


## 4. やり方のメモ

- 日付のずらし：スクラッチパッドの `at.sh`（node の `Date` を JST の指定時刻へ）と、ブラウザ用の `fakedate-pw.cjs`。FTUE の測定は `performance.timeOrigin + performance.now()`（両側とも実時間）で行うので、`Date` をずらしても測定は変わらない。
- 経済シミュレーションの結果が変わらないことは、`simulate()` の全項目を JSON で前後比較して確かめる（E1 は 64.2/65 と余裕が無いので、性能の変更で数字が動いてはいけない）。
