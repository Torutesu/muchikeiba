# 要件定義（ロジック・サーバー）

対象：本リポジトリが実装する**ロジックとサーバー**。UI・3D演出・Unityのシーン構成と既存実装への接続は本要件の対象外。
本書の要件IDは実装・テストから参照する（例：`// REQ-RACE-012`）。

---

## 0. 用語

| 用語 | 意味 |
|---|---|
| tick | レース計算の1ステップ。20Hz（50ms） |
| スロット | レース内の枠（0〜11）。ゲート番号＝スロット＋1 |
| 決定論 | 同じ設定と同じ入力なら、どの端末でも完全に同じ結果になること |
| ロックステップ | 全員の入力をtick単位で揃えてから各端末が計算を進める方式 |
| レース部屋 | 1レースを中継するサーバー上のオブジェクト（Durable Object） |
| プレイヤー部屋 | 1プレイヤーの財布・所持品を持つサーバー上のオブジェクト |
| 有償コイン／無償コイン | 購入で得たコイン／配布で得たコイン。法律上の扱いが違うため別管理 |
| 正規化 | ランク戦で馬の能力合計をクラス上限に圧縮すること |
| ルールセット | レース計算の調整値一式。サーバーが配り、全端末が同じものを使う |

## 1. レースエンジン（C#、端末と検証サーバーで共通）

### 1.1 決定論
- REQ-RACE-001 浮動小数点を一切使わない。全ての計算は64bit整数の固定小数点（Q16.16、単位はメートル・秒）で行う。
- REQ-RACE-002 乱数は自前の決定論的な乱数（PCG32等）のみ。シードはレース設定から与える。`System.Random`、時刻、`Dictionary`の列挙順など環境依存のものに結果が依存してはならない。
- REQ-RACE-003 計算は固定タイムステップ（20Hz）。描画のフレームレートと無関係に進む。
- REQ-RACE-004 物理エンジンを使わない。コースは1次元（スタートからの距離）＋横位置（レーン）で表す。
- REQ-RACE-005 エンジンは外部依存なし・`netstandard2.1`（Unity 2022.3以降で使える）。
- REQ-RACE-006 同じ設定・同じ入力で、任意の回数・任意の環境で再計算して同じ結果ハッシュになることをテストで保証する。

### 1.2 入力
- REQ-RACE-010 入力は1tickにつき1スロット1バイトのビットフラグ。
  - bit0 `START`：ゲートでのスタート
  - bit1 `LANE_IN`：内へ1レーン
  - bit2 `LANE_OUT`：外へ1レーン
  - bit3 `REIN_PRESS`：手綱を引き始める
  - bit4 `REIN_RELEASE`：手綱を緩める
  - bit5 `WHIP`：ムチ
  - bit6 `CPU_TAKEOVER`：このスロットをCPU操作に切り替える（サーバーだけが発行）
  - bit7 `HUMAN_RESUME`：人の操作に戻す（サーバーだけが発行）
- REQ-RACE-011 入力のないtickは「何もしない」。手綱は押した／離したの変化だけを送る（状態は保持される）。
- REQ-RACE-012 矛盾する入力（`LANE_IN`と`LANE_OUT`が同時など）は両方無視。`REIN_PRESS`と`REIN_RELEASE`が同時なら`RELEASE`を優先。

### 1.3 レースの流れ
- REQ-RACE-020 tick 0〜ゲートが開くまでは待機（カウントダウン）。ゲートが開くtickはルールセットの`gateOpenTick`。
- REQ-RACE-021 スタート反応：ゲートが開いたtickから`startReactionWindowTicks`以内に`START`を入れると加速ボーナス。早すぎる`START`（開く前）は無視し、出遅れ扱いにはしない（フライングの罰はない）。`START`を入れなかった馬は`autoStartDelayTicks`後に自動で出る。
- REQ-RACE-022 全頭がゴールするか、`maxTicks`に達したらレース終了。`maxTicks`に達した馬は未完走（順位は走った距離順で最後尾側）。
- REQ-RACE-023 ゴールのtick内での通過タイミングを固定小数点で記録し（tick内の何割の時点でゴールしたか）、同じtickにゴールした馬はその値で順位を決める。それも同じなら枠番の若い順。

### 1.4 馬の能力と状態
- REQ-RACE-030 能力値：`speed`（最高速）、`stamina`（脚の量）、`burst`（瞬発力＝直線の伸び）、`guts`（根性＝脚が尽きた後の粘り）、`temper`（気性＝折り合いの崩れにくさ）。各0〜1000の整数。
- REQ-RACE-031 脚質：`nige`（逃げ）／`senko`（先行）／`sashi`（差し）／`oikomi`（追込）。CPUの走り方と、位置ごとの折り合いのしやすさに影響。
- REQ-RACE-032 距離適性`distMinM`〜`distMaxM`、馬場適性`turf`/`dirt`/`both`。適性外は最高速と脚の量が下がる（割合はルールセット）。
- REQ-RACE-033 状態：距離、レーン（横位置）、速度、残り脚（スタミナ）、折り合い（0〜100）、残りムチ回数、ムチの効果残りtick、手綱の状態、ゴールtick。

### 1.5 走りのルール
- REQ-RACE-040 目標速度は「巡航」「手綱を引いている（減速・脚の消費減）」「スパート（最後の直線、または残り距離が`spurtDistanceM`以下）」で変わる。速度は加速度の上限つきで目標速度に近づく。
- REQ-RACE-041 脚の消費は速度の2乗に比例（ルールセットの係数）。脚が0になると最高速が`gutsFloor`（根性で決まる割合）まで落ちる。
- REQ-RACE-042 スリップストリーム：同じレーン（横位置の差が0.5レーン以内）で前方`slipstreamRangeM`以内に他の馬がいると、脚の消費が`slipstreamSavePermille`だけ減る。
- REQ-RACE-043 コーナーでは外のレーンほど実際に進む距離が短くなる（コーナー半径＋レーン位置×レーン幅の比で計算）。直線では差がない。
- REQ-RACE-044 進路妨害：同じレーンで前方`blockRangeM`以内に遅い馬がいると、その馬の速度を超えられない（抜くにはレーン変更が必要）。
- REQ-RACE-045 レーン変更：1回の入力で1レーン分を`laneChangeTicks`かけて移動。移動先の前後`laneChangeClearanceM`以内に馬がいる場合は移動できない（入力は無視）。レーンは0（最内）〜`laneCount-1`。
- REQ-RACE-046 折り合い：気性が低い馬は、道中にランダム（決定論乱数）で「かかる」。かかっている間は折り合いが下がり、脚の消費が増える（最大`badComposureExtraDrainPermille`）。手綱を引くと折り合いが回復する。折り合いが閾値以下だと消費増。
- REQ-RACE-047 ムチ：最大`maxWhips`回。1回ごとに`whipEffectTicks`の間、加速と最高速にボーナス。前のムチから`whipDiminishWindowTicks`以内の連打は効果が`whipDiminishPermille`に減る。スパート区間より前に使うと効果が小さく、折り合いが下がる。残り0回の`WHIP`は無視。
- REQ-RACE-048 最後の直線の伸び：スパート中の最高速ボーナスは`burst`と残り脚の割合で決まる。
- REQ-RACE-049 調整値は全てルールセット（`contracts/ruleset-params.default.json`）で持ち、コードに直書きしない。

### 1.6 CPU
- REQ-RACE-060 CPU馬の判断はエンジン内で決定論的に行う（乱数はスロットごとに派生したシードの決定論乱数）。サーバーも端末も同じCPUの動きになる。
- REQ-RACE-061 CPUは脚質に応じた目標位置（逃げ＝先頭、追込＝後方など）を取り、前が詰まったらレーンを変え、折り合いが悪いと手綱を引き、スパート区間でムチを間隔をあけて使う。
- REQ-RACE-062 CPUの強さは`cpuLevel`（1〜5）。判断の正確さ（タイミングのばらつき）だけを変え、能力値は変えない。
- REQ-RACE-063 `CPU_TAKEOVER`を受けた人のスロットは、そのtickからCPUの判断で走る（切断時の引き継ぎ）。

### 1.7 出力
- REQ-RACE-070 状態チェックサム：`checksumIntervalTicks`ごとに全馬の状態（スロット順に距離・レーン・速度・残り脚・折り合い・残りムチ・ゴールtick）をFNV-1a 64bitでハッシュし、16桁の小文字16進で出す。
- REQ-RACE-071 結果：着順（スロットの並び）、各馬のゴールtickとtick内の割合、着差（前の馬との距離）。
- REQ-RACE-072 結果ハッシュ：結果を正規化した文字列（`contracts/protocol.md`）のSHA-256（64桁の小文字16進）。
- REQ-RACE-073 リプレイ：設定＋入力ログから同じレースを再現できる。表示側（Unityクライアント）が任意tickの全馬の状態を取れるAPIを提供する。

### 1.8 表示側（Unityクライアント）へ渡すAPI
- REQ-RACE-080 毎tickの全馬の状態（距離・レーン・速度・残り脚の割合・折り合い・残りムチ・ムチ中か・手綱中か・順位・ゴール済みか）を読み取り専用で取れる。
- REQ-RACE-081 表示用に、tick間の補間に使える前tickの状態も取れる。
- REQ-RACE-082 コース上の距離から3D座標への変換は表示側の責任。エンジンはコースの区間（直線／コーナーと半径）を公開する。
- REQ-RACE-083 実況用のイベント（ゲートが開いた、出遅れ、先頭が変わった、かかった、ムチ、スパート開始、ゴール、着順確定）をtick付きで出す。

## 2. ロックステップ通信（C#クライアント＋TSレース部屋）

- REQ-NET-001 時間はレース部屋が進める。部屋は`startAtMs`を基準に、50msごとのtickを確定させ、そのtickの全員の入力（無い人は0）を配る。
- REQ-NET-002 端末は入力を「現在の確定tick＋`inputDelayTicks`（既定3＝150ms）」宛てに送る。既に確定したtick宛ての遅れた入力は、次に確定するtickに回す。
- REQ-NET-003 部屋は確定したtickを`bundleIntervalTicks`（既定2）ごとにまとめて送る（入力が0のtickは省略、範囲で表す）。
- REQ-NET-004 端末は確定済みのtickだけを計算する。届いていないtickは待つ（表示は補間で滑らかにする）。
- REQ-NET-005 端末は`checksumIntervalTicks`ごとにチェックサムを送る。部屋は多数派と違う端末を「ズレ」として記録し、その端末に通知する。
- REQ-NET-006 切断：一定時間（`disconnectGraceMs`）応答がない人のスロットは、部屋が`CPU_TAKEOVER`を入力として挿入し、全員の計算でCPUに切り替わる。
- REQ-NET-007 再接続：端末は最後に計算したtickを伝え、部屋はそれ以降の確定入力をまとめて送る。端末は早送りで追いつき、部屋は`HUMAN_RESUME`を挿入して操作を戻す。
- REQ-NET-008 ゴール後、各端末は結果ハッシュと着順を送る。部屋は次の規則で確定する。
  - 結果を送った人が2人以上で、同じハッシュが送った人の2/3以上かつ2人以上 → 確定
  - 人が1人だけのランク戦、多数派がない、通報がある、抜き取り（`verifySampleRate`）に当たった → 検証サーバーで再計算した結果で確定
  - 検証サーバーにもつながらない場合 → 無効（報酬なし・レート変動なし）
- REQ-NET-009 部屋は入力ログ（設定＋全入力）を保存する（検証と通報対応のため。保存期間は設定値）。
- REQ-NET-010 メッセージ形式は`contracts/protocol.md`に従う。部屋のロジックは通信方式に依存しない純粋なクラスとして実装し、Durable ObjectはWebSocketとの橋渡しだけをする。
- REQ-NET-011 部屋は待機中にWebSocket休止機能を使い、時間課金を発生させない（レース中のみアラーム／タイマーで進める）。

## 3. 検証サーバー（C#）
- REQ-VER-001 設定＋入力ログを受け取り、同じエンジンで再計算して結果ハッシュ・着順・チェックサムを返す。CLIとHTTPの両方。
- REQ-VER-002 入力ログの形式違反・ルールセット不一致は400エラー。
- REQ-VER-003 1レースの再計算は1秒未満（目標：数十ms）。

## 4. マッチング（TS）
- REQ-MM-001 ランク戦は待ち行列。レート（Glicko-2）の近い人から組む。待ち時間に応じて許容するレート差を広げる。
- REQ-MM-002 最大12人。`cpuFillAfterMs`（既定15秒）で揃わなければ空き枠をCPUで埋めて開始する。最低1人の人間がいれば開始。
- REQ-MM-003 初心者（ランク戦の経験が`beginnerRaces`未満）は初心者同士＋CPUで組み、CPUの強さを下げる。
- REQ-MM-004 フレンド部屋：合言葉で集まり、ホストが開始する。レート変動なし。
- REQ-MM-005 レース開始時、サーバーがレース設定を作る（シード＝暗号学的乱数、コース、出走馬の能力（ランク戦は正規化後）、ルールセット）。

## 5. レート・クラス（TS）
- REQ-RATE-001 Glicko-2。多人数レースは「人間同士の全ペアの勝ち負け」に分解して更新する。CPUとの結果はレートに入れない。
- REQ-RATE-002 クラス（例：C級→B級→A級→S級）は月次シーズンのポイントで昇級・降級する。シーズン終了時に確定。
- REQ-RATE-003 ランク戦の正規化：クラスごとの能力合計上限`classStatCap`。合計が上限を超える馬は各能力を同じ比率で縮める（整数・切り捨て、脚質と適性は変えない）。

## 6. プレイヤーの財布とコイン（TS）
- REQ-WAL-001 有償コインと無償コインを別々の残高で持つ。全ての増減を追記専用の台帳（取引ID・種別・有償/無償・増減・残高・理由・時刻）に記録する。
- REQ-WAL-002 消費は**有償から先**に使う（資金決済法上の未使用残高を減らすため。ショップに表示する）。有償限定の商品は有償残高のみ使う。
- REQ-WAL-003 残高はマイナスにならない（返金処理の例外を除く。6.3参照）。
- REQ-WAL-004 全ての付与・消費は冪等キーを持ち、同じキーの二重処理をしない。
- REQ-WAL-005 全プレイヤーの有償コイン未使用残高を日次で集計できる（基準日の1,000万円判定用）。円換算は購入時の単価で行う。

### 6.2 購入
- REQ-PUR-001 購入前に「購入してよいか」をサーバーに問い合わせる（年齢確認済みか、月額上限内か、1回限りの商品を買っていないか）。
- REQ-PUR-002 年齢確認：初回購入前に生年月を登録。年齢帯（16歳未満／16〜19歳／20歳以上）ごとの月額上限は設定値（金額はJOGAの指針を見て決める。未確定は設定ファイルに仮値）。未成年は保護者同意のチェックが必須。
- REQ-PUR-003 ストアのレシートをサーバーで検証し（Apple App Store Server API／Google Play Developer API。アダプタ経由）、取引IDで冪等に付与する。
- REQ-PUR-004 初回購入ボーナス：商品ごとに初回だけ有償コイン2倍（ボーナス分は無償として付与するか有償とするかは設定。既定は無償）。
- REQ-PUR-005 スターターパックは1回限り。シーズンパスは有効期限つきの購読状態として持つ。
- REQ-PUR-006 返金（ストアからの取り消し通知）：付与した有償コインを差し引く。足りない場合は不足分を「未精算」として記録し、精算までガチャと購入を止める。

## 7. ガチャ（TS、抽選は必ずサーバー）
- REQ-GACHA-001 ガチャの定義（排出物・レア度・個別の提供割合（ppm、合計1,000,000）・価格・10連の保証・天井）は1つのデータで持つ。
- REQ-GACHA-002 提供割合の表示データは、抽選に使うのと同じ定義から自動生成する。10連の保証枠の割合も別に表示する。
- REQ-GACHA-003 定義の検証：割合の合計が1,000,000でない、存在しない馬、価格0、保証の条件が満たせない、などは読み込み時にエラー。
- REQ-GACHA-004 10連は10枠目に「SR以上確定」の保証（それまでの9枠にSR以上がなかった場合のみ保証テーブルで引く）。
- REQ-GACHA-005 天井：引くたびに交換ポイント1。100で対象（ピックアップ）と交換できる。ポイントはガチャごと（または同じグループ）で管理し、期間終了時の扱いは設定（既定：別の交換先に変換）。
- REQ-GACHA-006 ダブり（同じ馬を既に持っている）は覚醒素材に変換する。
- REQ-GACHA-007 抽選の乱数は暗号学的乱数。テストでは差し替えられる。
- REQ-GACHA-008 コンプガチャ防止：報酬・ミッションの定義で「有償ガチャでしか出ない物を複数そろえる」条件があれば読み込み時にエラー。
- REQ-GACHA-009 抽選結果・使ったコイン（有償/無償の内訳）・天井ポイントを1つの取引として記録する（途中で失敗したら全て巻き戻る）。
- REQ-GACHA-010 初回10連無料（チュートリアル）は1回限り。

## 8. 馬・配合（TS）
- REQ-HORSE-001 馬は個体として持つ（ID、元の種類、レア度、能力、覚醒段階、性別、生年、父母ID、現役/引退）。
- REQ-HORSE-002 覚醒：覚醒素材を使って能力の上限を段階的に上げる（ランク戦では正規化されるため、主にフレンド戦・タイムアタック・配合の素質に効く）。
- REQ-HORSE-003 命名：カタカナ2〜9文字。NGリスト（実在の有名馬名・団体名・レース名・不適切語）に当たる名前は拒否。ひらがな→カタカナ、小書き文字、長音の揺れを正規化して照合する。
- REQ-HORSE-004 引退：現役の馬を引退させると繁殖馬（牡＝種牡馬、牝＝繁殖牝馬）になる。
- REQ-HORSE-005 配合：種牡馬×繁殖牝馬で仔を生産。1日1回（設定値）。仔の能力は両親の平均を基準に、素質（覚醒段階）と乱数で上下（上限・下限あり）。脚質・距離適性は両親から確率で受け継ぐ。
- REQ-HORSE-006 ニックス（相性の良い血統の組み合わせ）は表で持ち、成立すると能力にボーナス。
- REQ-HORSE-007 血統表：5代まで辿れる。近親配合（3代以内に同じ馬）には能力のペナルティ。
- REQ-HORSE-008 配合の予想表示（脚質・距離の範囲・継承率の目安）は、実際の計算と同じ関数から作る。

## 9. 報酬・ミッション・シーズン（TS）
- REQ-REW-001 レース報酬は着順・モードで決まる。ランク戦はシーズンポイントも付与。
- REQ-REW-002 ログインボーナス（7日間）、デイリーミッション、初心者ミッション。
- REQ-REW-003 シーズンパス：無料ライン／有料ライン。レベルはパス経験値で上がる。購入時に即時報酬。

## 10. 認証・API（TS）
- REQ-API-001 認証はFirebase AuthのIDトークン（匿名ログインを基本、引き継ぎにApple/Google）。WorkersでJWT署名を検証する（Googleの公開鍵、`aud`=プロジェクトID、`iss`、有効期限）。
- REQ-API-002 全APIは入力をスキーマで検証し、不正な入力は400。
- REQ-API-003 プレイヤー部屋への書き込みは冪等キー必須。
- REQ-API-004 エラーは機械が読めるコード（例：`INSUFFICIENT_COINS`、`AGE_LIMIT_EXCEEDED`）で返す。

## 11. 非機能要件

| ID | 要件 |
|---|---|
| NFR-001 | レースエンジンの1tick計算は12頭で0.1ms未満（端末の負担を無視できる） |
| NFR-002 | 1レースの通信量：端末→部屋は入力の変化時のみ、部屋→端末は100msごとのまとめ送信 |
| NFR-003 | 待機中のサーバー費用はゼロに近い（休止機能、常時稼働サーバーなし） |
| NFR-004 | プレイヤー数が増えても構成を変えずに増やせる（部屋単位で独立） |
| NFR-005 | お金と抽選に関わる処理は全てサーバー。端末の値は信用しない |
| NFR-006 | 全てのロジックに自動テスト。決定論・お金・ガチャの確率は重点的にテスト |
| NFR-007 | 調整値（ルールセット、ガチャ定義、上限金額など）はコード外の設定データ |
| NFR-008 | 個人情報は最小限（生年月のみ。氏名・住所は持たない） |
