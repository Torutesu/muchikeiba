# 要件定義（ロジック・サーバー）

対象：本リポジトリが実装する**ロジックとサーバー**。UI・3D演出・Unityのシーン構成と既存実装への接続は本要件の対象外。
本書の要件IDは実装・テストから参照する（例：`// REQ-RACE-012`）。

---

## 0. 用語

| 用語 | 意味 |
|---|---|
| tick | レース計算の1ステップ。20Hz（50ms） |
| スロット | レース内の枠（0〜11）。ゲート番号＝スロット＋1 |
| 決定論 | 同じ設定と同じ入力なら、どの端末でも完全に同じ結果になること |
| ロックステップ | 全員の入力をtick単位で揃えてから各端末が計算を進める方式 |
| レース部屋 | 1レースを中継するサーバー上のオブジェクト（Durable Object） |
| プレイヤー部屋 | 1プレイヤーの財布・所持品を持つサーバー上のオブジェクト |
| 有償コイン／無償コイン | 購入で得たコイン／配布で得たコイン。法律上の扱いが違うため別管理 |
| 正規化 | ランク戦で馬の能力合計をクラス上限に圧縮すること |
| ルールセット | レース計算の調整値一式。サーバーが配り、全端末が同じものを使う |

## 1. レースエンジン（C#、端末と検証サーバーで共通）

### 1.1 決定論
- REQ-RACE-001 浮動小数点を一切使わない。全ての計算は64bit整数の固定小数点（Q16.16、単位はメートル・秒）で行う。
- REQ-RACE-002 乱数は自前の決定論的な乱数（PCG32等）のみ。シードはレース設定から与える。`System.Random`、時刻、`Dictionary`の列挙順など環境依存のものに結果が依存してはならない。
- REQ-RACE-003 計算は固定タイムステップ（20Hz）。描画のフレームレートと無関係に進む。
- REQ-RACE-004 物理エンジンを使わない。コースは1次元（スタートからの距離）＋横位置（レーン）で表す。
- REQ-RACE-005 エンジンは外部依存なし・`netstandard2.1`（Unity 2022.3以降で使える）。
- REQ-RACE-006 同じ設定・同じ入力で、任意の回数・任意の環境で再計算して同じ結果ハッシュになることをテストで保証する。

### 1.2 入力
- REQ-RACE-010 入力は1tickにつき1スロット1バイトのビットフラグ。
  - bit0 `START`：ゲートでのスタート
  - bit1 `LANE_IN`：内へ1レーン
  - bit2 `LANE_OUT`：外へ1レーン
  - bit3 `REIN_PRESS`：手綱を引き始める
  - bit4 `REIN_RELEASE`：手綱を緩める
  - bit5 `WHIP`：ムチ
  - bit6 `CPU_TAKEOVER`：このスロットをCPU操作に切り替える（サーバーだけが発行）
  - bit7 `HUMAN_RESUME`：人の操作に戻す（サーバーだけが発行）
- REQ-RACE-011 入力のないtickは「何もしない」。手綱は押した／離したの変化だけを送る（状態は保持される）。
- REQ-RACE-012 矛盾する入力（`LANE_IN`と`LANE_OUT`が同時など）は両方無視。`REIN_PRESS`と`REIN_RELEASE`が同時なら`RELEASE`を優先。

### 1.3 レースの流れ
- REQ-RACE-020 tick 0〜ゲートが開くまでは待機（カウントダウン）。ゲートが開くtickはルールセットの`gateOpenTick`。
- REQ-RACE-021 スタート反応：ゲートが開いたtickから`startReactionWindowTicks`以内に`START`を入れると加速ボーナス。早すぎる`START`（開く前）は無視し、出遅れ扱いにはしない（フライングの罰はない）。`START`を入れなかった馬は`autoStartDelayTicks`後に自動で出る。
- REQ-RACE-022 全頭がゴールするか、`maxTicks`に達したらレース終了。`maxTicks`に達した馬は未完走（順位は走った距離順で最後尾側）。
- REQ-RACE-023 ゴールのtick内での通過タイミングを固定小数点で記録し（tick内の何割の時点でゴールしたか）、同じtickにゴールした馬はその値で順位を決める。それも同じなら枠番の若い順。

### 1.4 馬の能力と状態
- REQ-RACE-030 能力値：`speed`（最高速）、`stamina`（脚の量）、`burst`（瞬発力＝直線の伸び）、`guts`（根性＝脚が尽きた後の粘り）、`temper`（気性＝折り合いの崩れにくさ）。各0〜1000の整数。
- REQ-RACE-031 脚質：`nige`（逃げ）／`senko`（先行）／`sashi`（差し）／`oikomi`（追込）。CPUの走り方と、位置ごとの折り合いのしやすさに影響。
- REQ-RACE-032 距離適性`distMinM`〜`distMaxM`、馬場適性`turf`/`dirt`/`both`。適性外は最高速と脚の量が下がる（割合はルールセット）。
- REQ-RACE-033 状態：距離、レーン（横位置）、速度、残り脚（スタミナ）、折り合い（0〜100）、残りムチ回数、ムチの効果残りtick、手綱の状態、ゴールtick。

### 1.5 走りのルール
- REQ-RACE-040 目標速度は「巡航」「手綱を引いている（減速・脚の消費減）」「スパート（最後の直線、または残り距離が`spurtDistanceM`以下）」で変わる。速度は加速度の上限つきで目標速度に近づく。
- REQ-RACE-041 脚の消費は速度の2乗に比例（ルールセットの係数）。脚が0になると最高速が`gutsFloor`（根性で決まる割合）まで落ちる。
- REQ-RACE-042 スリップストリーム：同じレーン（横位置の差が0.5レーン以内）で前方`slipstreamRangeM`以内に他の馬がいると、脚の消費が`slipstreamSavePermille`だけ減る。
- REQ-RACE-043 コーナーでは外のレーンほど実際に進む距離が短くなる（コーナー半径＋レーン位置×レーン幅の比で計算）。直線では差がない。
- REQ-RACE-044 進路妨害：同じレーンで前方`blockRangeM`以内に遅い馬がいると、その馬の速度を超えられない（抜くにはレーン変更が必要）。
- REQ-RACE-045 レーン変更：1回の入力で1レーン分を`laneChangeTicks`かけて移動。移動先の前後`laneChangeClearanceM`以内に馬がいる場合は移動できない（入力は無視）。レーンは0（最内）〜`laneCount-1`。
- REQ-RACE-046 折り合い：気性が低い馬は、道中にランダム（決定論乱数）で「かかる」。かかっている間は折り合いが下がり、脚の消費が増える（最大`badComposureExtraDrainPermille`）。手綱を引くと折り合いが回復する。折り合いが閾値以下だと消費増。
- REQ-RACE-047 ムチ：最大`maxWhips`回。1回ごとに`whipEffectTicks`の間、加速と最高速にボーナス。前のムチから`whipDiminishWindowTicks`以内の連打は効果が`whipDiminishPermille`に減る。スパート区間より前に使うと効果が小さく、折り合いが下がる。残り0回の`WHIP`は無視。
- REQ-RACE-048 最後の直線の伸び：スパート中の最高速ボーナスは`burst`と残り脚の割合で決まる。
- REQ-RACE-049 調整値は全てルールセット（`contracts/ruleset-params.default.json`）で持ち、コードに直書きしない。

### 1.5.1 馬場状態・ダート・ナイター
- REQ-RACE-034 馬場状態：芝は firm（良・硬め）/ good（良）/ yielding（稍重）/ soft（重）、ダートは fast（良・乾燥）/ good（良）/ muddy（稍重）/ sloppy（不良）。最高速と脚の消費に効く（係数はルールセット）。芝の重は良より勝ち時計が3〜6%遅い。ダートは同じ距離の芝より遅く、湿るほど速く前が残りやすい。指定がなければ good。
- REQ-RACE-035 得意馬場：馬に `goingAptitude`（any / fast / heavy）。合う馬場で最高速が少し上がり、逆の馬場で下がる。配合では両親から確率で受け継ぎ、配合予想は実際の配合と同じ確率を返す。
- REQ-RACE-036 ナイター：照明のある競馬場の夜のレース。計算には影響せず、表示と実況（ゲート前の馬場・照明の一言）だけに使う。
- REQ-RACE-037 その日の馬場：ランク戦とフレンド戦では、JSTの日付とコースから決まる馬場を使う（同じ日・同じコースは誰でも同じ）。重みと運営の上書き（期間・コース指定）はマスター／リモート設定で変えられる。チュートリアルとタイムアタックは馬場の指定なし（良・昼）。
- REQ-RACE-038 互換性：馬場の項目と追加したルールセットのキーがない古い設定・リプレイは、これまでと1バイトも違わない結果になる（ゴールデンの旧版で常に検証する）。

### 1.6 CPU
- REQ-RACE-060 CPU馬の判断はエンジン内で決定論的に行う（乱数はスロットごとに派生したシードの決定論乱数）。サーバーも端末も同じCPUの動きになる。
- REQ-RACE-061 CPUは脚質に応じた目標位置（逃げ＝先頭、追込＝後方など）を取り、前が詰まったらレーンを変え、折り合いが悪いと手綱を引き、スパート区間でムチを間隔をあけて使う。
- REQ-RACE-062 CPUの強さは`cpuLevel`（1〜5）。判断の正確さ（タイミングのばらつき）だけを変え、能力値は変えない。
- REQ-RACE-063 `CPU_TAKEOVER`を受けた人のスロットは、そのtickからCPUの判断で走る（切断時の引き継ぎ）。

### 1.7 出力
- REQ-RACE-070 状態チェックサム：`checksumIntervalTicks`ごとに全馬の状態（スロット順に距離・レーン・速度・残り脚・折り合い・残りムチ・ゴールtick）をFNV-1a 64bitでハッシュし、16桁の小文字16進で出す。
- REQ-RACE-071 結果：着順（スロットの並び）、各馬のゴールtickとtick内の割合、着差（前の馬との距離）。
- REQ-RACE-072 結果ハッシュ：結果を正規化した文字列（`contracts/protocol.md`）のSHA-256（64桁の小文字16進）。
- REQ-RACE-073 リプレイ：設定＋入力ログから同じレースを再現できる。表示側（Unityクライアント）が任意tickの全馬の状態を取れるAPIを提供する。

### 1.8 表示側（Unityクライアント）へ渡すAPI
- REQ-RACE-080 毎tickの全馬の状態（距離・レーン・速度・残り脚の割合・折り合い・残りムチ・ムチ中か・手綱中か・順位・ゴール済みか）を読み取り専用で取れる。
- REQ-RACE-081 表示用に、tick間の補間に使える前tickの状態も取れる。
- REQ-RACE-082 コース上の距離から3D座標への変換は表示側の責任。エンジンはコースの区間（直線／コーナーと半径）を公開する。
- REQ-RACE-083 実況用のイベント（ゲートが開いた、出遅れ、先頭が変わった、かかった、ムチ、スパート開始、ゴール、着順確定）をtick付きで出す。

## 2. ロックステップ通信（C#クライアント＋TSレース部屋）

- REQ-NET-001 時間はレース部屋が進める。部屋は`startAtMs`を基準に、50msごとのtickを確定させ、そのtickの全員の入力（無い人は0）を配る。
- REQ-NET-002 端末は入力を「現在の確定tick＋`inputDelayTicks`（既定3＝150ms）」宛てに送る。既に確定したtick宛ての遅れた入力は、次に確定するtickに回す。
- REQ-NET-003 部屋は確定したtickを`bundleIntervalTicks`（既定2）ごとにまとめて送る（入力が0のtickは省略、範囲で表す）。
- REQ-NET-004 端末は確定済みのtickだけを計算する。届いていないtickは待つ（表示は補間で滑らかにする）。
- REQ-NET-005 端末は`checksumIntervalTicks`ごとにチェックサムを送る。部屋は多数派と違う端末を「ズレ」として記録し、その端末に通知する。
- REQ-NET-006 切断：一定時間（`disconnectGraceMs`）応答がない人のスロットは、部屋が`CPU_TAKEOVER`を入力として挿入し、全員の計算でCPUに切り替わる。
- REQ-NET-007 再接続：端末は最後に計算したtickを伝え、部屋はそれ以降の確定入力をまとめて送る。端末は早送りで追いつき、部屋は`HUMAN_RESUME`を挿入して操作を戻す。
- REQ-NET-008 ゴール後、各端末は結果ハッシュと着順（任意で各馬のゴールtick）を送る。部屋は次の規則で確定する。
  - 人間が2人以上のレース：**全員の報告が同じハッシュ**で、それが2人以上かつ**人間スロット全体の2/3以上** → 確定
  - 人間が1人：チュートリアル・フレンドは確定、ランク戦は検証
  - 人間が2人以上なのに報告が1人だけ、多数派がない、**1人でも違うハッシュを報告した**、通報がある、抜き取り（`verifySampleRate`）に当たった → 検証サーバーで再計算した結果で確定（違うハッシュを多数決で退けると、結託した複数アカウントが正直なプレイヤーを「不正の疑い」にできてしまうため）
  - 検証サーバーに届かない場合は再試行（3回、間隔を倍々）し、それでもだめなら無効（報酬なし・レート変動なし）
- REQ-NET-009 部屋は入力ログ（設定＋全入力）を保存する（検証と通報対応のため。保存期間は設定値）。
- REQ-NET-010 メッセージ形式は`contracts/protocol.md`に従う。部屋のロジックは通信方式に依存しない純粋なクラスとして実装し、Durable ObjectはWebSocketとの橋渡しだけをする。
- REQ-NET-011 部屋は待機中にWebSocket休止機能を使い、時間課金を発生させない（レース中のみアラーム／タイマーで進める）。
- REQ-NET-012 1件の`res`で部屋を止めない（早すぎる・偽の結果で他の人を止める嫌がらせの防止）。部屋がtickを止めて判定するのは、接続中の人間全員が報告した時、接続中の人間の過半数が報告してから`resultWaitMs`経った時、`maxTicks`に達した時のいずれか。最も速い馬でもゴールできないtick（`gate + 距離 ÷ 全ボーナス込みの最高速`）より前の`res`は`RESULT_TOO_EARLY`で拒否。各端末の最初の`res`だけを採用（後から差し替え不可）。
- REQ-NET-013 ソケットが閉じなくても、`disconnectGraceMs`の間メッセージが来ない端末は切断扱いにしてCPUへ引き継ぐ（結果を報告済みの端末は対象外）。再びメッセージが来たら操作を戻す。
- REQ-NET-014 部屋の状態は、入力のまとめ（`b`）・`final`・`desync`を送る前、フェーズが変わる時、`hello`・`res`の時に永続化する（再起動で確定済みtickをやり直さない）。検証・精算はアラームからだけ実行し、各段階を永続化してから次へ進む（二重検証・二重付与をしない）。プレイヤーへの反映に失敗した人だけを後で再試行する。

## 3. 検証サーバー（C#）
- REQ-VER-001 設定＋入力ログを受け取り、同じエンジンで再計算して結果ハッシュ・着順・チェックサムを返す。CLIとHTTPの両方。
- REQ-VER-002 入力ログの形式違反・ルールセット不一致は400エラー。
- REQ-VER-003 1レースの再計算は1秒未満（目標：数十ms）。

## 4. マッチング（TS）
- REQ-MM-001 ランク戦は待ち行列。レート（Glicko-2）の近い人から組む。待ち時間に応じて許容するレート差を広げる。
- REQ-MM-002 最大12人。`cpuFillAfterMs`（既定15秒）で揃わなければ空き枠をCPUで埋めて開始する。最低1人の人間がいれば開始。
- REQ-MM-003 初心者（ランク戦の経験が`beginnerRaces`未満）は初心者同士＋CPUで組み、CPUの強さを下げる。
- REQ-MM-004 フレンド部屋：合言葉で集まり、ホストが開始する。レート変動なし。
- REQ-MM-005 レース開始時、サーバーがレース設定を作る（シード＝暗号学的乱数、コース、出走馬の能力（ランク戦は正規化後）、ルールセット）。1人が同時に参加できるレースは1つ（進行中は待ち行列・チュートリアル・フレンド戦の開始を`ALREADY_IN_RACE`で拒否、精算時に解除）。
- REQ-MM-006 フレンド部屋は人間2人以上でないと開始できない（`ROOM_TOO_SMALL`）。部屋は永続化する。レースの開始に失敗した待ち行列の人は待ち時間を保ったまま戻す。
- REQ-MM-007 マッチングの状態（待ち行列・割り当て・フレンド部屋・イベントの待ち行列）は**1行ずつ**SQLiteに保存し、変わった行だけを書く（1つの値にまとめると2 MiBの上限で全員のマッチングが止まるため）。フレンド部屋は**ホスト1人につき1つ**（作り直すと同じ部屋が返る）、全体の上限つき、期限切れはあらゆる操作のたびに掃除する。
- REQ-MM-008 マッチしたプレイヤーは、レース部屋を作る（非同期の）前に「開始中」の印を同期的に付ける。この間の待ち行列への参加・イベントの取り消し・フレンド戦の開始は`ALREADY_IN_RACE`で拒否し、作成に失敗したら印を外して待ち行列（またはフレンド部屋）に戻す。フレンド戦・チュートリアルの開始時は、全メンバーがランク戦・イベントの待ち行列にいないことも確認する。

## 5. レート・クラス（TS）
- REQ-RATE-001 Glicko-2。多人数レースは「人間同士の全ペアの勝ち負け」に分解して更新する。CPUとの結果はレートに入れない。
- REQ-RATE-002 クラス（例：C級→B級→A級→S級）は月次シーズンのポイントで昇級・降級する。シーズン終了時に確定。
- REQ-RATE-003 ランク戦の正規化：クラスごとの能力合計上限`classStatCap`。合計が上限を超える馬は各能力を同じ比率で縮める（整数・切り捨て、脚質と適性は変えない）。
- REQ-RATE-004 レート更新は、マッチング時のレートとの差分として反映する（その後にレートが動いていても古い値で上書きしない）。

## 6. プレイヤーの財布とコイン（TS）
- REQ-WAL-001 有償コインと無償コインを別々の残高で持つ。全ての増減を追記専用の台帳（取引ID・種別・有償/無償・増減・残高・理由・時刻）に記録する。
- REQ-WAL-002 消費は**有償から先**に使う（資金決済法上の未使用残高を減らすため。ショップに表示する）。有償限定の商品は有償残高のみ使う。
- REQ-WAL-003 残高はマイナスにならない（返金処理の例外を除く。6.3参照）。
- REQ-WAL-004 全ての付与・消費は冪等キーを持ち、同じキーの二重処理をしない。
- REQ-WAL-005 全プレイヤーの有償コイン未使用残高を日次で集計できる（基準日の1,000万円判定用）。円換算は購入時の単価で行う。

### 6.2 購入
- REQ-PUR-001 購入前に「購入してよいか」をサーバーに問い合わせる（年齢確認済みか、月額上限内か、1回限りの商品を買っていないか）。
- REQ-PUR-002 年齢確認：初回購入前に生年月を登録。年齢帯（16歳未満／16〜17歳／18〜19歳／20歳以上）ごとの月額上限は設定値（金額はJOGAの指針を見て決める。未確定は設定ファイルに仮値）。成年年齢（18歳）未満は保護者同意のチェックが必須。

### 8.1 種牡馬の貸し借り・隔世遺伝・季節限定の馬（TS＋C#、`src/domain/stud.ts`・`studService.ts`・`horses.ts`）

- REQ-BREED-011 探す：フレンドの登録馬（公開範囲を問わず）と、全体公開の登録馬（自分の馬は除く）を新しい順に表示。一覧は検索用の写しで、持ち主のデータが正。
- REQ-BREED-012 種付けは2人のデータにまたがる取引として、同じ操作ID（`stud:<借り手>:<冪等キー>`）で ①持ち主が枠を確保（公開範囲・1日上限を確認、馬の写しを返す）②借り手が料金の支払い・配合・未送金の記録を1回で確定 ③持ち主が料金を受け取り記録 ④借り手が未送金を消す、の順に進める。各段階は何度繰り返しても結果が同じ（二重請求・二重支払い・料金の消失なし）。同じ冪等キーは確保した種牡馬・借り手に結び付き、別の馬・別の借り手での再利用は `CONFLICT`。借り手は画面で見た料金を `expectedFee` で送れ、持ち主がその後に料金を変えていたら `FEE_CHANGED`（何も確保・請求しない）。ストア購入で付いた無償コイン（初回購入ボーナス・サンドボックス分）は購入から90日間は種付け料に使えない（返金時の回収前に他人へ移さないため。支払い後もその分は残っている必要がある）。②が失敗したら①の枠を戻す。③④が届かなければ借り手のDurable Objectのアラームが間隔を伸ばしながら再送する。確保だけ残った枠は `reserveTtlMs` で失効する（誰も請求されていない）。
- REQ-BREED-013 借りた種牡馬での配合は通常の配合と同じ計算（能力の基準・ニックス・近親・ばらつき・距離・馬場適性・見た目）で行い、その日の配合回数に数える（配合素材による追加も可）。借り手は1日 `borrowPerDay` 回まで。
- REQ-BREED-014 血統：仔には持ち主と種牡馬ID（`studSire`）を記録し、血統表では他人の種牡馬を全員共通のキー（`stud:<持ち主>:<馬ID>`）とその父母名で表す。同じ種牡馬の血を引く牝馬との配合は近親として数える。持ち主側は誰に貸し、どの仔が生まれたかを履歴に残す。
- REQ-BREED-015 上限：持ち主が1日に受け取れる種付け料は `dailyEarnCap` まで（超えた分は支払われず消える）。リモート設定でも法的・経済上の上限（`STUD_HARD_LIMITS`）は超えられない。有償コインは種付け料に使えず、持ち主は有償コインを受け取らない。
- REQ-BREED-016 借りる前の予想表示は、通常の予想と同じ関数で作り、料金・残り枠・支払えるかを添える。
- REQ-BREED-017 隔世遺伝：祖父母が持つ脚質・馬場適性のうち、両親のどちらも持たないものを、配合ごとに `atavismPermille`（既定40‰）の確率で1つ受け継ぐ。能力値は変えない（バランスを崩さない）。候補がいない配合では乱数を一切追加で使わず、従来と同じ結果になる。抽選は他のすべての抽選の後。
- REQ-BREED-018 隔世遺伝の確率表示は実際の抽選と同じ関数（`atavismOptions`・`atavismOdds`）から作る（候補ごとに確率を等分）。
- REQ-BREED-019 祖父母は自分の厩舎にいる馬だけを数える（ガチャ産の馬の父母は不明＝候補なし）。借りた種牡馬は持ち主の厩舎の父母を写しに含める。
- REQ-BREED-020 季節限定の馬：馬の定義に期間（`seasonal`）を持たせる。期間内に開く、その馬を明示したバナー（`seasonal`）と、期間内のイベント報酬からだけ手に入る。恒常バナー・券の抽選表・CPUの出走馬には出ない。

- REQ-BREED-022 イベント報酬に馬（テンプレートID）を指定できる。設定の検証で、未知の馬・期間外のイベントの限定馬を弾く。

### 9.2 シーズンの締め（TS）
- REQ-SEASON-001 月の切り替わり（JST）後、定期実行で前シーズンを締める。最終順位を確定してから、参加者を1人ずつ処理する。

- REQ-SEASON-004 失敗し続ける1人（または1チーム）が後ろの全員を止めないよう、同じ相手が`MAX_ROLLOVER_ATTEMPTS`（5回の実行）続けて失敗したら運用向けの未処理リスト（`deadLetter`）に移してカーソルを進める。定期実行は各ステップを個別に例外処理し、直近3シーズンのうち締め終わっていないものを毎回進める。1回の実行は時間の予算内でバッチを繰り返す。

### 9.6 タイムアタック・ゴースト（TS＋C#）
- REQ-TA-001 開始：サーバーがセッションを発行する（シード＝暗号学的乱数、コース、ルールセット、出走は自分の馬1頭のみ・CPUなし、`mode`=`timeattack`）。プレイヤーと結び付いた短期の署名トークン（HMAC、有効期限＝`sessionTtlMs`）を返す。
- REQ-TA-002 馬の能力は`timeAttack.statCap`で正規化する（ランク戦と同じ方式）。脚質・適性は変えない。
- REQ-TA-003 提出：端末は**入力だけ**（`[tick, 0, cmd]`、スロット0のみ、クライアントのビットのみ、tick は厳密に増加・`maxTicks`未満、件数上限`maxInputs`）と自分で計算した結果ハッシュを送る。サーバーは**自分が発行した設定**で検証サーバーに再計算させ、ハッシュが一致した時だけ記録する。1セッション1回。期限切れ・使用済み・別プレイヤーのトークンは拒否。設定を送り返した場合、発行した設定と1か所でも違えば拒否（キー順は問わない）。ハッシュ不一致は記録せず拒否（再提出不可）。同じセッション・同じハッシュの再送は保存済みの結果を返す（通信の再試行に安全）。検証サーバーに届かない時は`VERIFIER_UNAVAILABLE`で、期限内なら同じセッションを再提出できる。
- REQ-TA-004 1日（JST）の開始回数は`maxAttemptsPerDay`まで。
- REQ-TA-005 記録：タイムはゲートが開いてからゴールまで（`(finishTick − gateOpenTick) × 50ms + finishFrac × 50ms / 65536`、端末の`OfflineRace.FinishTimeMs`と同一式）。シーズン（JST月）ベストと通算ベストをコースごとに持つ。速さは (finishTick, finishFrac) で比較する。
- REQ-TA-006 ランキング：シーズン×コースのボード`ta-<trackId>`を、ランク戦と同じ定期集計でR2に公開する（上位`topN`、自分の順位は集計時点）。遅い記録が速い記録を上書きすることはない。
- REQ-TA-007 自己ベストの節目報酬（`timeAttack.milestones`、コース別の秒数・初完走）は各1回だけ。
- REQ-TA-009 タイムアタックの設定は、その時有効なリモート設定のルールセット（調子の揺らぎなし、`+ta`）で発行する。セッションの設定に丸ごと入るため、走っている途中で設定が変わってもその走りには影響せず、検証サーバーは発行時のルールセットで再計算する。
- REQ-TA-008 ゴースト：シーズンベストを更新した走りは、検証済みのリプレイログ（設定＋入力）をR2 `ghosts/<seasonId>/<trackId>/<playerId>.json` に保存する。一覧は「上位」「フレンド」「自分」の3種。ゴーストは**別のシミュレーション**として自分の走りと同じtickで並走させ、プレイヤーの馬には一切影響しない（スリップストリーム・進路妨害なし）。再生すると記録と同じゴールtickになる。

### 9.7 運用（TS）
- REQ-OPS-001 リプレイログは`replayRetentionDays`（既定30日）を過ぎたら毎日の定期実行で削除する。ただし通報・不一致（容疑者あり／ズレ）・検証で確定・無効のレースは保留（R2の`customMetadata.hold`）にして残す。削除処理は一覧の位置（カーソル）を保存して次の実行で続きから再開し、末尾まで来たら先頭に戻る（毎回先頭からだと、件数が増えたとき後ろの期限切れに届かないため）。
- REQ-OPS-001a 保留にも期限を設ける：「検証で確定」（`verified`）の保留は`replayHoldDays.verified`（既定90日）で期限切れにして削除する。通報・不一致・ズレ・無効は運用が対応するまで残す（期限なし）。保留ごとの日数はリモート設定で変えられる。ゴースト（`ghosts/`）は別の置き場で、この削除の対象外。

### 9.7 設定配信（リモートコンフィグ、TS）
- REQ-OPS-002 アプリ更新なしで変えられる設定（レースのルールセット、ガチャのバナーと開催日程・天井グループ、コース、進行系マスター（報酬・上限など）、NGリスト）を「バンドル」として版管理する。各版は内容のSHA-256（キー順を正規化したJSON）で識別し、保存後は変更できない。同じ内容を再登録すると既存の版を返す。
- REQ-OPS-003 版の登録時に、起動時と同じ検証を行う：ルールセットのキー集合が`contracts/ruleset-params.default.json`と一致・値は32bit整数、ガチャの提供割合の合計・存在しない馬・天井グループ、コンプガチャ検出、コースの区間合計＝距離、進行系マスターの未知キー。値を変えたのに`rulesetVersion`を変えていない／同じ`rulesetVersion`を別の値で再利用する場合も拒否する。
- REQ-OPS-004 版の有効化は「今すぐ」または「指定時刻」。効果が出る前の予約は取り消せる。ロールバックは1つ前の版、指定した版、または組み込みの既定（base）に即時に戻す。全ての操作は履歴に残る。
- REQ-OPS-005 Worker・各Durable Objectは有効な設定を30秒（または次の予約時刻まで）キャッシュし、バンドル本体は自分が知らない版のときだけ受け取る。設定の配信元に障害があっても、最後に知っている設定（なければ既定）で動き続ける。
- REQ-OPS-006 レース設定には、その時有効なルールセットが丸ごと入る。リプレイログにもそのまま残るので、後からルールセットを変えても過去のレースは同じ値で検証できる。
- REQ-OPS-007 `GET /v1/config` で有効な版（versionId・hash・rulesetVersion・有効化時刻）を返す。アプリはhashごとにマスターデータをキャッシュし、変わったら取り直す。

### 9.8 管理API（TS）
- REQ-OPS-010 管理APIの認証は、トークン（設定には平文でなくSHA-256だけを`ADMIN_TOKENS`に置く）またはCloudflare AccessのJWT（チームドメイン・AUD・メール→権限の対応表）。旧`ADMIN_TOKEN`は権限adminとして残す。
- REQ-OPS-011 権限は viewer（閲覧）＜ operator（サポート操作・設定の登録）＜ admin（設定の有効化・ロールバック、BAN）。足りなければ403 `FORBIDDEN`。
- REQ-OPS-012 書き込み操作は理由（3〜500文字）が必須。全ての管理操作（閲覧を含む）を監査ログに残す：誰が・権限・操作・対象・理由・変更前・変更後・成否・時刻。失敗や権限不足も記録する。
- REQ-OPS-013 管理APIは操作者ごとにレート制限する（閲覧と書き込みで別枠）。超えたら429 `RATE_LIMITED`。
- REQ-OPS-014 監査ログは操作者・対象・操作で絞り込み、新しい順にページングして読める。

### 9.9 サポート（TS）
- REQ-OPS-020 プレイヤー検索：財布（有償ロット・円換算の残高）、台帳（直近）、購入履歴、月別の支払額、年齢と年齢帯、サポート用の印、購読、不正対策の状態を表示する（冪等キャッシュは出さない）。
- REQ-OPS-021 お詫び配布：無償コインとアイテムのみ（有償コインは作らない）。操作キーで冪等。権限ごとの上限（operator：1回1万コイン・アイテム100個、admin：10万・1000個）。台帳に操作者と理由を残す。
- REQ-OPS-022 一括配布：プレイヤーIDの一覧、またはランキングのスナップショット（シーズン・ボード・範囲）を対象に、1回200人まで・合計100万コインまで。受け取る人ごとに冪等（同じ操作キーで再実行しても二重にならない）。続きの位置を返す。
- REQ-OPS-023 返金負債の免除：コインとアイテムの負債を指定量まで免除し、台帳に0円の`settle`行と理由を残す。
- REQ-OPS-024 年齢の訂正：アプリからは「若くなる方向」しか変えられない年齢（REQ-PUR-002）を、本人確認のうえサポートが訂正できる。サポート用の印を残す。
- REQ-OPS-025 名前のリセット：不適切な表示名・馬名を既定の名前に戻す。

### 9.10 不正対策の運用（TS）
- REQ-OPS-030 レース確定後、結果が食い違った人（容疑者）とチェックサムがズレた人を不正対策の記録に送る（レース単位で冪等。チュートリアルは対象外）。
- REQ-OPS-031 7日間の重み付き点数（容疑者1、ズレ0.5）が3以上で自動的に隔離（14日。再発で延長）。期間が過ぎれば自動で解除。運用者が手動で解除でき、その際は期間内の記録を消す。
- REQ-OPS-032 隔離中のプレイヤーは、ランク戦で隔離中の人同士かCPUとだけ組まれる。フレンド戦・購入は制限しない。
- REQ-OPS-033 BANは管理者だけが行う（期限つき／無期限）。BAN中はランク戦・フレンド部屋に入れず、購入前チェックで403 `BANNED`。ストアで支払い済みのレシートは付与し、サポート用の印を付ける（返金はサポートで対応）。
- REQ-OPS-034 プレイヤーの通報はレビュー用の列に入る（レースと通報者の組で重複なし）。通報だけで隔離・BANにはしない。運用者が結論を付けて閉じる。
- REQ-OPS-035 隔離・BAN・解除の状態はプレイヤー本人のオブジェクトに反映され、マッチングと購入の判定に使われる。反映は送信待ちの列（1プレイヤー1行、新しい判断が古いものを置き換える）を経由し、失敗したら不正対策オブジェクトのアラームで再送する（判断が反映されないまま失われない）。
- REQ-OPS-036 レースの精算（各プレイヤーへの結果反映）は`MAX_SETTLE_ATTEMPTS`（10回）で打ち切り、反映できなかったプレイヤーは運用向けの未処理リスト（`deadLetter`）に記録してアラームを止める。
- REQ-OPS-040 実在の登録服色と同じ（または紛らわしい）勝負服は使えない。一覧は`server/master/banned-silks.json`（出典と形式を記載、現在は空）。照合は模様・色の別名（「襷」→sash、「青」→blue）と色の系統（紺≒青、海老≒赤など）で正規化した組み合わせで行う。プレイヤーの勝負服の変更・初期値の生成で拒否する。管理APIから一覧を丸ごと取り込める（検証→アクティブな設定に重ねて新しい版として登録。有効化は通常の設定変更と同じ別操作）。
- REQ-OPS-041 失敗リスト（dead letter）の運用：シーズン締め（プレイヤー／支部）、イベントの順位報酬、レースの精算、隔離・BANの反映で、自動の再試行回数を超えて脇に置かれた項目を、OpsDOの索引で一覧できる。本体は各オブジェクトが持ち、管理APIで中身の確認（索引も更新）、再試行（下の処理はどれも冪等）、メモ付きの取り下げ（手作業で対応済み）ができる。再試行はoperator、取り下げはadmin。操作はすべて監査ログに残る。

### 9.11 プッシュ通知（TS）
- REQ-PUSH-001 FCM HTTP v1で送る。認証はサービスアカウントのJWT→OAuthトークン（キャッシュ）。設定が無い環境では送らずに捨てる。
- REQ-PUSH-002 個別通知：フレンド申請が届いた、フレンドが成立した、フレンド部屋に招待された。文言は日本語テンプレート（マスターデータ）で、相手の表示名を差し込む（合言葉は通知に載せない）。
- REQ-PUSH-003 端末登録：1人複数台（上限`maxDevices`、最後に使った順に残す）。登録・解除のAPIを持つ。
- REQ-PUSH-004 受信設定：種類（season / friends / invites / events）ごとのオン・オフ、静かな時間帯（JST）、1日の上限。静かな時間帯は急ぎの通知を捨て、それ以外は明けるまで遅らせる。
- REQ-PUSH-005 送信はプレイヤーのDurable Objectのアラームで行い、リクエスト処理を待たせない。無効な端末（UNREGISTERED / INVALID_ARGUMENT など）は削除し、一時的な失敗はバックオフして再送、上限回数またはTTLで諦める。送り先の端末やテンプレートが無くなった通知は送信時刻に捨てる（残すと毎秒アラームが鳴り続けるため）。アラームでもリモート設定のテンプレートを使う。
- REQ-PUSH-006 シーズンのお知らせ（開幕・終了N日前・最終日）は毎日12:07 JSTの定期実行で判定し、FCMトピックへ1回だけ送る。購読するトピックは受信設定のAPIが返す。

### 9.12 KPI計測（TS）
- REQ-KPI-001 イベントは Workers Analytics Engine に固定の列配置で書く。JOINができないため、各行にインストール日（JST）・インストールからの日数・課金者かどうかを含める。
- REQ-KPI-002 サーバーで分かるイベント（初回起動・ログインボーナス・購入（初回フラグ付き）・返金・パスの更新と状態・ガチャ・レース結果・シーズン締め・フレンド）は、処理が保存された場合だけ出す。
- REQ-KPI-003 クライアントイベントは受け付ける種類を限定してスキーマで検証する（最大50件/回）。サーバーで分かるイベントはクライアントから受け付けない。
- REQ-KPI-004 1人あたりの受付上限（30回/分、2,000件/日）。範囲外の時刻のイベントは捨てる。
- REQ-KPI-005 個人情報を含めない。プレイヤーIDはソルト付きハッシュに置き換え、ソルトが無ければ書き込まない。
- REQ-KPI-006 継続率（D1/D7/D30）・チュートリアルの通過率・初回課金の転換率と日数・ARPDAU・課金率・パスの継続・課金者と無課金者のランク戦勝率差を出すクエリを用意する（`docs/ops/kpi-queries.md`）。

### 9.13 支部（チーム戦、TS）
- REQ-TEAM-001 支部を作れる（名前2〜12文字・NGリスト・URL禁止）。作った人がリーダー。1人が入れる支部は1つだけ。
- REQ-TEAM-002 加入方針は「自由（すぐ加入）」か「承認制（申請→リーダー／幹部が承認）」。申請は支部ごとに上限（`maxPendingRequests`）と期限（`requestTtlMs`）、プレイヤーごとに同時申請の上限（`maxOutgoingRequests`）。承認時に申請者が他の支部に入っていた・待機中だった場合は申請を取り消す。
- REQ-TEAM-003 役職はリーダー・幹部（`maxOfficers`人まで）・メンバー。リーダーは全操作、幹部は承認／却下・メンバーの除名・お知らせの編集ができる。幹部は他の幹部やリーダーを除名できない。
- REQ-TEAM-004 リーダーはメンバーが残っている間は抜けられない（`TEAM_LEADER_MUST_TRANSFER`）。譲渡すると元リーダーは幹部になる。解散はリーダーが最後の1人のときだけ。リーダーが1人で抜けると解散。
- REQ-TEAM-005 支部ポイント＝メンバーのランク戦シーズンポイントのうち「加入後に獲得した分」の合計。1人分は`memberPointsCap`で頭打ち（強い1人のキャリーを防ぐ）。脱退・除名されたメンバーの分は支部から外れる。
- REQ-TEAM-006 チャットは無し。リーダー・幹部が書く短いお知らせ（`announcementMax`文字、NGリスト・URL禁止）だけ。
- REQ-TEAM-007 不正な乗り換え対策：自分で抜けると`rejoinCooldownMs`の間は他の支部に入れない（除名・解散ではかからない）。シーズン報酬は、シーズン終了の`rewardMinDays`日前までに加入し、終了時に在籍していた人だけ（終了後に抜けた人は対象のまま）。
- REQ-TEAM-008 月次シーズンが終わると、支部の最終順位に応じた報酬（`seasonRewards`、0ポイントの支部は対象外）を対象メンバーに1回だけ配る。定期実行で中断しても続きから再開でき、二重に配らない。
- REQ-TEAM-009 支部ランキングはシーズンごとにR2のスナップショットで公開（`leaderboards/<season>/teams.json`）。支部名での検索と、今シーズン活発な支部の一覧を提供する。
- REQ-TEAM-010 承認制の申請が届いたらリーダー・幹部に、承認されたら申請者にプッシュ通知（種類 friends）。
- 規模の設計：1支部＝1 Durable Object（支部ごとに独立して直列化、支部同士は競合しない）。検索用ディレクトリは要約だけを持つ単一オブジェクト、ランキングはシーズンごとの LeaderboardDO に同居。

### 9.14 イベントレース（TS＋C#）
- REQ-EVENT-001 イベント定義（期間・コース・参加条件・参加費・特別ルール・ポイント・報酬）は `master/events.json` かリモートコンフィグで差し替える。読み込み・登録時に検証（存在しないコース、ルールセットにないキー、`rulesetVersion`/`maxTicks` の変更、有償コインの参加費などはエラー）。
- REQ-EVENT-002 参加条件：期間中であること、クラス、ランク戦の経験回数、馬の脚質。一覧APIで「参加できるか・できない理由」を返す。
- REQ-EVENT-003 特別ルールはルールセットの値の上書き（例：`maxWhips`=0）・全頭の能力固定・能力合計の上限・CPUの強さ。上書きがあると `rulesetVersion` は「元の版+ev.<id>」になり、設定ごと検証サーバーに渡るので同じルールで再計算される（`contracts/protocol.md` §8.2）。
- REQ-EVENT-004 参加費は無償コインかチケットのみ（有償コインで賞品を競う形は作らない）。キュー登録時に預かり、キャンセル・マッチング拒否・無効レースでは返す。30分以上使われずに残った預かりは自動で返す。同じ冪等キーでの再送は二重に取らない。
- REQ-EVENT-005 ポイント＝着順ポイント＋参加ポイント。到達ポイントごとの報酬（マイルストーン）は1回だけ。レース結果の反映はレースIDで冪等。
- REQ-EVENT-006 マッチングはイベントごとに別の待ち行列（ランク戦の人とは混ざらない）。人数とCPU補完までの時間はイベントごとの設定。結果の合意・検証はランク戦と同じ（人間1人なら必ず検証）。
- REQ-EVENT-007 イベントランキングはR2のスナップショットで公開（`events/<id>/board.json`、ポイント→勝利数→先に到達した順）。
- REQ-EVENT-008 終了（＋確定待ち15分）後、最終順位の報酬を1回だけ配る。定期実行で中断しても再開でき、二重に配らない。終了時に残っていた参加費の預かりは返す。
- REQ-EVENT-009 開始時にイベント用トピックへ1回だけプッシュ通知（開始から6時間以内のみ）。

### 9.15 アセットの取り決め（TS＋C#、`contracts/assets.md`）
- REQ-ASSET-001 アセットキーは小文字英数字と`_`の段を`/`でつないだ文字列（最低2段、作り直しは`@vN`）。kind は最後の段を除いた部分。サーバー（`visuals.ts`）とクライアント（`AssetKeys.cs`）は同じ規則でキーを作る。
- REQ-ASSET-002 キーが見つからない場合は `<kind>/default` → 何も表示しない、の順で必ず続行する（落とさない）。全 kind の既定アセットは最初のダウンロードに含める。
- REQ-ASSET-003 馬は見た目（毛色・顔・脚4本・たてがみ・体型）を持つ。テンプレート馬は固定、古いセーブの馬は読み込み時に決まった規則で付与し、以後変えない。所持馬一覧・ガチャ結果で返す。
- REQ-ASSET-004 配合の仔は形質ごとに父母のどちらかから受け継ぎ、低確率で突然変異（芦毛は親が芦毛なら約半分）。乱数は配合の他の抽選の後に引く（能力などの結果は変わらない）。
- REQ-ASSET-005 勝負服は模様＋パレット色（模様ごとに2〜3色、同色のみ不可）＋帽子。一部の模様はコスチュームアイテムで解放。実在の登録服色と同じ組み合わせは禁止リストで拒否。既定の勝負服は無料の模様だけで、禁止リストに当たらない。
- REQ-ASSET-006 レースの `start` メッセージに全馬の見た目・枠番・馬名の音声キー・コースのシーン（回り・馬場・夜）を `visuals` として付ける。レース設定・結果ハッシュ・リプレイログには入れない（見た目の変更が検証に影響しない）。
- REQ-ASSET-007 コースの3D形状は表示専用（浮動小数点、`Muchi.Client` のみ）。距離は内ラチに沿い、レーンは外向きの垂直な横ずれ、コーナーは半径＋横ずれの円弧（エンジンのコーナーロスと一致）。左回り・右回りは競馬場ごと。支部エンブレムは決まったパーツの組み合わせのみ。
- REQ-ASSET-008 マスターデータが参照しうる全キーを `contracts/assets.manifest.json` に生成する（`npm run gen:assets`）。マスターとマニフェストのずれ、形式違反、既定アセットの欠落はテストで失敗させる。初回ダウンロードは小さく、残りは必要時にCDNから取得する。
- REQ-ASSET-010 実在の登録服色の勝負服は禁止（REQ-OPS-040）。
- REQ-ASSET-009 実況の音声キーは定型フレーズの断片・数字・馬名（馬IDではなく馬名のFNV-1a 64bit）から作る。馬名の音声は命名時に生成するため動的。

### 9.16 アイテム・見た目の直販（TS＋C#、`server/master/items.json`）
- REQ-ITEM-001 ガチャ券（`gacha_ticket`）：対象ガチャ（`tickets.gacha_ticket.banners`、有償限定ガチャは不可＝読み込み時に検証）を1回引ける。抽選はそのガチャの提供割合と同じ表で行い、天井ポイントを1加算する。ガチャの提供割合表示に「この券で引ける」ことを出す。
- REQ-ITEM-002 SR以上確定券（`ticket_sr_plus`）：券専用の表（SR以上のみ、合計1,000,000ppm）で1頭引く。表示（`GET /v1/items/tickets/:itemId/odds`）は抽選と同じ定義から作る。天井ポイントは加算しない。
- REQ-ITEM-003 配合素材（`breeding_material`）：その日の通常の配合を使い切った後、素材`cost`個で1日`extraPerDay`回まで追加で配合できる。仔の能力の抽選は通常と同じ（ランク戦の公平性に影響しない）。配合の予想に今日の残り回数を出す。
- REQ-ITEM-004 見た目アイテムの一覧（`GET /v1/shop/cosmetics`）：勝負服の模様の解放・馬具（頭絡・ゼッケン布）・厩舎の飾り。価格・通貨・所持・装備中・アセットキーを返す。能力には影響しない。
- REQ-ITEM-005 見た目アイテムはコインで直接買う（確率なし）。各1回まで（`ALREADY_PURCHASED`）。有償から先に消費し、「有償限定」の品は有償コインのみ。
- REQ-ITEM-006 装備（`PUT /v1/player/equipment`）：馬具は枠（`bridle`/`saddlecloth`）ごとに1つ、飾りは`decorSlots`枠まで（重複不可）。所持していない物・枠違いは拒否。`null`で外す。装備した馬具は公開プロフィールに載る。アセットキーの種類 `tack/*`・`decor/*` を追加（`contracts/assets.md`）。
- REQ-ITEM-007 勝負服の模様の解放アイテムを直販し、買うと`PUT /v1/player/silks`でその模様を選べる。
- REQ-ITEM-008 券・素材の消費と見た目アイテムの購入は、アイテムの台帳（`itemLog`、直近200件）に残す。券の使用・購入は冪等キー必須、返金による負債（コイン・アイテム）があるあいだは使えない。

### 9.16.1 マイ厩舎（TS＋C#、`src/domain/stable.ts`、`server/master/stable.json`、docs/planning/06 §7.2・REQ-UXS-060）
- REQ-STABLE-001 厩舎の配置：テーマ（壁・床、`stable/theme/<id>`）・表札・飾り枠（テーマごとの枠数。既定テーマは今の `decorSlots` と同じ3枠）・馬房に立たせる馬（`featuredMax` 頭まで。選ばなければ現役馬の上位）・トロフィー棚（称号・戦績・大会の成績から自動）。設定はプレイヤーのデータに保存する。
- REQ-STABLE-002 保存（`PUT /v1/stable`）は持っている厩舎の飾りだけを置ける（REQ-ITEM-006 と同じ検証）。テーマは解放済みのものだけ、馬は自分の現役馬だけ。表札は表示名と同じNGチェック。
- REQ-STABLE-003 訪問者が見るのは公開用の写し（`StableSnapshot`）で、DirectoryDO の `stables` 表（持ち主のシャード）に置く。訪問で持ち主のDurable Objectは読まない。写しは持ち主のトランザクションのたびに作り直して差分があれば書く（表示名・称号・勝負服・馬の名前・引退・利用停止・いいね数が反映される）。写しに財布・所持品・購入は含めない。
- REQ-STABLE-004 訪問：フレンドの厩舎と、おすすめ（いいねの多い順、自分・フレンド・空の厩舎は除く、`recommendedLimit` 件、全シャードから集めて1分キャッシュ）。見るだけで、持ち物の受け渡しはない。
- REQ-STABLE-005 いいね：1日 `likesPerDay` 回（既定5）、同じ相手には1日 `likesPerTargetPerDay` 回（1）、自分には押せない。冪等キー必須。押す側の段階（上限の確認と記録）で決まる `likeId` を相手側は1回だけ数え、相手側でも同じ人からの1日の回数を確かめる。2段目が失敗しても同じキーの再送で完了する。

- REQ-STABLE-007 モデレーション：利用停止（banned）のプレイヤーの厩舎は写しから消え（訪問・いいね不可）、保存もいいねもできない。表札は保存時にNGチェックし、NGリストが増えたら写しでは表札を出さない。サポートは `POST /v1/admin/players/:playerId/name-reset` の `target: "stable"` で表札を消せる。勝負服は公開プロフィールと同じく登録済みの実在勝負服を避けた見た目になる。
- REQ-STABLE-008 設定（`server/master/stable.json`）はリモート設定の `stable` で丸ごと差し替えられ、読み込み時と同じ検証（上限・既定テーマがちょうど1つで解放条件なし・テーマIDの形式・解放アイテムの存在）を通す。
- REQ-STABLE-009 アカウント削除：`StableService.removeStable(playerId)` が公開用の写しを消す（持ち主のDurable Objectには触れない）。配置といいね数はプレイヤーのデータの一部として一緒に消える。配置だけ消すときは `stableClear`。

### 9.19 支部対抗シーズン（TS＋C#、`src/domain/league.ts`）
- REQ-LEAGUE-001 月次シーズンごとに支部どうしのリーグを1つ行う（そのシーズンの `lb:<seasonId>` が持つ）。部（`progression.json league.divisions`、上から順）に分かれ、前のシーズンの昇格・降格の結果から始まる。初めて参加する支部は一番下の部から。月を `weeks` 個の週（7日ごと、最後の週は月末まで）に区切って対戦する。
- REQ-LEAGUE-002 各週の始まりに、部ごとに順位（勝ち点 → 得失点差 → 支部のシーズンポイント）の近い支部どうしを組む（同じポイント帯どうし）。前の週と同じ相手はできるだけ避け、奇数なら1支部は不戦（`byePoints`）。参加できるのはその時点でメンバーが `minMembers` 人以上の支部。週の始まりから `lateEntryHours` 以内に条件を満たした支部（月替わりでまだ誰も走っていない支部など）は、不戦の枠か、遅れて来た支部どうしで組む。
- REQ-LEAGUE-003 対戦の得点は、その週のあいだにメンバーのランク戦で支部への貢献（REQ-TEAM-005 の上限・加入時点の差し引き込みなので、強い1人だけでは勝てない）がどれだけ増えたか。メンバーの在籍期間ごとに週の始まりの値を記録して増えた分を足すので、週の途中で抜けたメンバーの分も抜けた時点の値で残る（抜けても支部のその週の得点は減らない）。勝ち `winPoints`・引き分け `drawPoints`・負け `lossPoints`。終わった週は定期実行で集計し、定期実行が止まっていて一度も始まらなかった週は「中止」（後から集計しない）。何度実行しても同じ結果。
- REQ-LEAGUE-004 シーズンが終わると支部の締め（REQ-TEAM-008）の最初に最終順位を確定し、各部の上位 `promote` が昇格、下位 `relegate` が降格（一番上・一番下の部を除く）。順位に応じたリーグ報酬（`league.rewards`、部と順位ごと）は支部のシーズン報酬と同じ支払い（同じ在籍日数ルール、同じ「シーズンごとに1回」の記録、同じ失敗リスト・再実行）で配る。支部のシーズン報酬がない（0ポイント）支部でも、リーグの順位があればリーグ報酬は配る。
- REQ-LEAGUE-005 `GET /v1/league/me`：自分の支部の部・順位表・週ごとの対戦（相手・得点・勝敗）・シーズン後の最終順位と報酬と次の部。部ごとの順位表と対戦は R2 のスナップショット（`leaderboards/<season>/league-<divisionId>.json`、`GET /v1/leaderboards/:seasonId/league-<divisionId>`、認証なし）。
- REQ-LEAGUE-006 リーグの設定はリモートコンフィグで差し替え可能。読み込み時に検証（部IDの重複・勝ち点の大小・報酬の部・アイテム）。起動時にも同梱の設定を検証する。リーグ報酬と支部のシーズン報酬に入れられるのは無償コインとアイテムだけ（馬や知らないキーは読み込み時に拒否。支部の締めの支払いでは馬を渡せないため）。

### 9.23 大会（TS＋C#、`src/domain/tournaments.ts`、`src/do/tournament.ts`）
- REQ-TOUR-001 大会は運営が管理APIで作る（operator、理由と監査つき）：名前・コース・受付開始/締切・開始時刻・ヒートの人数（2〜12）・出走頭数（CPU補完込み）・勝ち上がり人数・定員・最少人数・参加条件・能力上限・CPUの強さ・ラウンド間隔・通知の時刻・賞品。存在しないコース・クラス・アイテムは `400`。締切は開始の30秒以上前。
- REQ-TOUR-002 エントリーは受付期間中だけ、定員まで。再エントリーは馬の変更（順番は最初の登録時刻のまま）。取り消しも受付期間中だけ。
- REQ-TOUR-003 参加条件：クラス・ランク戦の回数・脚質・現役の馬・隔離/BANでないこと（プレイヤー側のデータで判定、理由を返す）。能力上限は全出走馬に適用（`RaceStartConfig.statCap`）。
- REQ-TOUR-004 組み分け：受付締切で、レート（同じなら登録順）のスネーク順にヒートへ均等に分ける。端数のヒートは上位シードが少人数。
- REQ-TOUR-005 進行は大会ごとの Durable Object のアラーム（cron は保険）。ヒートのレース部屋は開始30秒前に作り、選手の席は `/v1/tournaments/:id/me` と `/v1/match/status` に出る。ヒートは `mode: "tournament"`（ranked と同じ合意・検証、人間1人なら必ず検証、レートは動かない）。
- REQ-TOUR-006 勝ち上がり：ヒートの人間の着順で上位 `advancePerHeat` 人（2人以上のヒートは必ず1人以上が敗退）。一度も接続しなかった選手は CPU が走り、勝ち上がれない。無効のヒート・消えた部屋（開始20分で打ち切り）は来た選手をシード順で勝ち上げる。勝ち上がりが1人ならその選手が優勝、0人ならそこで終了。
- REQ-TOUR-007 最終順位：決勝の着順、その後は到達ラウンドが遅い順・不参加は後・ヒートの着順。同じラウンドで同じ着順の敗退者は同順位（1-2-3-3-5）。賞品は順位の区分で、プレイヤーごとに大会IDで1回だけ（再試行しても二重にならない）。5回失敗したら失敗リスト（`tournament`）へ、運用から再試行・取り下げ。
- REQ-TOUR-008 各ラウンドの開始 `notifyBeforeMs`（既定5分）前に出場者へプッシュ「まもなく1回戦／決勝」（`tournament_heat_soon`、時刻に意味があるので静かな時間帯は送らない）。
- REQ-TOUR-009 一覧（受付前・受付中・開催中→最近の結果）、詳細（組み合わせ・結果・順位。R2 にも公開）、自分の状況（今のヒートとチケット・敗退・順位・賞品）、自分の大会成績（最大50件）。チケットは本人にしか見せない。
- REQ-TOUR-010 運営は表彰前なら中止できる（賞品なし）。進行の途中（レース部屋の作成・結果の確認・通知の待ち時間）に中止が届いても、進行はその場で止まり、「中止」を上書きせず、順位・賞品も出さない。
- REQ-TOUR-011 状態の大きさ：定員 `maxEntrants` は最大1024。定員いっぱいで全員が勝ち上がり枠まで進んだときの全ラウンドの出走枠の合計は定員の3倍まで（例：12人組なら勝ち上がりは7人まで。12人中11人のような設定は数十ラウンドになるので作成時に `400`）。この範囲なら最悪でも状態全体（組み合わせ・結果・順位・賞品の記録、登録を除く）は 1 MB 未満（テストで実測、約0.84 MB）。Durable Object には登録・ヒート・賞品の支払いを1件ずつ別の行、順位を1つの値、残り（状態・ラウンドの見出し）を小さな1つの値として保存し、変わった行だけを書く。レースのチケットは保存せず、`/me` のときに本人の分だけ作る（同じ部屋・枠・開始時刻から同じチケットになる）。
- REQ-TOUR-012 レース部屋の作成：ヒートの raceId は `t-<大会ID>-<ヒートID>-<試行回数>` で決まり、試行回数は部屋を作る前に保存する。作成中に再起動しても同じ試行（同じ raceId）を続けるので、部屋は2つできない（部屋の初期化は raceId ごとに1回だけで、既にあれば今の部屋の設定と開始時刻を使う）。作成が失敗したと分かったときだけ次の試行（新しい raceId）。作成の締切（開始から5分で無効）はラウンドの予定開始時刻から数え、作成が成功するまでヒートの開始時刻は動かさない。
- REQ-TOUR-013 参加条件の再確認：ヒートを作るとき、選手ごとに BAN・隔離と馬（現役か・まだいるか）をもう一度確かめる。外れた選手は不参加（CPU は入るが勝ち上がれない）。プレイヤーのデータに一時的に届かないだけなら登録時の内容で出走させる（障害で誰も脱落させない）。全員外れたヒートは部屋を作らずに無効。

## 13. ルールセット 1.1（バランス調整、docs/spec/balance-targets.md）
- REQ-RACE-039 その日の調子：各馬の最高速をレースごとにシードから決まる ±`conditionVariancePermille`‰ で揺らす。タイムアタックとチュートリアルでは0。
- REQ-RACE-050 騎手の自動の内寄せ：安全な時は `autoRailIntervalTicks` ごとに1レーン内へ寄る。プレイヤーが内外を操作した後 `autoRailHoldTicks` の間はしない。スパート区間ではしない。
- REQ-RACE-064 CPUのレベル別の癖：レベル ≤ `cpuSloppyMaxLevel` は初心者の癖（スタートが遅い、ムチが不規則、脚の温存なし）。レベル3 ≈ 初心者、レベル4・5は上手い人に近い。
- REQ-RACE-065 新しいキーは全部あるか全部ないかの任意キー群で、ない場合は1.0.xと同じ結果（保存済みのリプレイ・ゴーストを検証し続けるため）。
- REQ-BAL-001 レースのバランス目標（R1〜R8）と経済の目標（E1〜E10）を自動テストで常にチェックする。
- REQ-TA-009 タイムアタックのメダル秒数は、上手い人・初心者のモデルのシミュレーションから決める（金＝上手い人の上位10%、銀＝上手い人の中央値、銅＝初心者の中央値）。

## 14. ルールセット 1.2（脚質の距離による偏り、docs/spec/balance-targets.md 2章）
- REQ-RACE-051 距離で変わる量：スタミナ量とスパート区間の長さは、レースの距離 ÷ 基準距離（芝 `distanceRefM`、ダート `distanceRefDirtM`）に `staminaDistanceScalePermille`・`spurtDistanceScalePermille` の割合で比例させる。どの距離のコースでも脚質の有利不利が同じになるように（全コース×全馬場で脚質別勝率が一様の±25%、REQ-TRACK-002）。チュートリアル（400mの直線）では比例させない。
- REQ-RACE-052 新しいキーは全部あるか全部ないかの任意キー群で、ない場合は1.1.x以前と同じ結果（REQ-RACE-065 と同じ理由）。

## 15. UX・課金体験（TS、docs/planning/06 §5・§6.8・§6.9・§10.1）
法務の拘束条件（docs/planning/03・04）：換金・譲渡なし、コンプガチャなし、表示はデータから自動生成、有償・無償の分別管理（資金決済法）、特商法の表示、年齢帯の月額上限（金額は未確定のまま `age-limits.json`）。API の形は `contracts/protocol.md` §13。

- REQ-UXS-010 1日の初勝利ボーナス：その日（JST）の最初の勝利（1着）を3回まで、無償コインを上乗せ（既定 +30 / +20 / +10、`progression.firstWinBonus`）。対象はランク戦だけ（フレンド戦は稼ぎ口にしない、E9）。無効レースは数えない。`GET /v1/missions` の `firstWinBonus` に今日の残りを返す。経済目標 E1〜E9 を再計算し、ミッション「1勝」とパス無料ラインを下げて目標内に戻した（balance-targets.md 4.2）。
- REQ-UXS-017 オファーの状態 `GET /v1/shop/offers`：スターター（T2）は「ランク戦で初めて4着以下」か「ランク戦5戦目の後」の早い方で出す。シーズンパス（T3）はランク戦3戦（ショップ・パスの開放）以降、1シーズン1回。昇級記念パック（T4）はそのクラスに到達したら1回。表示した記録は `POST /v1/shop/offers/:offerId/view`（最初の時刻を保持、冪等）。購入済みの商品（1回限り・そのシーズンのパス・期間中の厩舎手当）のオファーは返さない。初回購入ボーナス（T1）は、まだボーナスの残っているコインのパックを返す。終了時刻は実在の期間（シーズンの終わり）だけ。
- REQ-UXS-018 厩舎手当（30日、¥480）：購入時に有償100、購入日から30日（JSTの日付）の間、1日1回 無償30を受け取れる（`POST /v1/shop/allowance/claim`、受け取らなかった日の分は後から受け取れない）。自動更新なし。期間中は購入できない（`ALREADY_PURCHASED`）。アプリを通さずに期間中の2つ目が届いたら、今の期間の翌日から始める（支払った日数は失われない、サポート用の印）。ストアでは消費型（Google は consume）。返金では有償100と受け取った無償コインを全て差し引き（足りなければ未精算）、以後は受け取れない。受け取った無償コインは購入から90日は種付け料に使えない（REQ-BREED-015 の保留と同じ）。
- REQ-UXS-019 昇級記念パック（¥1,500：有償1,020＋そのクラスの記念勝負服の柄、B・A・S級で各1回、クラス未到達は `NOT_ELIGIBLE`）と、シーズンパス＋（¥2,400：パス＋購入時に10段＋限定馬具。馬具はコインでは買えない）。パスとパス＋は1シーズンにどちらか1つ。1回限りの商品はストアで非消費型（Google は acknowledge）。アプリを通さずに再購入された1回限りの商品も、支払いは完了しているので付与し、サポート用の印を残す。
- REQ-UXS-020 シーズンパスは「シーズン（暦月）限り・自動更新なし」：有効期限＝付与した時点のシーズンの終わり（月末の購入がシーズン終了後に届いたら新しいシーズン分）。購入確認（`purchase-intent`）に `pass.remainingDays`・`lastWeek`（残り7日以内）を返す。パス画面（`GET /v1/season-pass`）はサーバーの値だけで描ける形（30段の報酬・期間・残り日数・購入できる商品）にする。旧来の自動更新の購読（ストアの期間を正とする）は過去の購入のためだけに残す。
- REQ-UXS-021 シーズン締めで、受け取っていないパス報酬を自動付与：到達したレベルのうち未受け取りの無料ライン、パスがシーズン終了まで有効なら有料ラインも。シーズンの切り替え（`rollSeason`）と同じトランザクションで付与とリセットを行うので二重には払わない。締めの定期処理（`closeSeason`、失敗はデッドレター REQ-OPS-041 で再試行）か、そのプレイヤーの次のリクエストの早い方で実行され、結果は `passHistory` と `closeSeason` の `pass` に残る。返金では、そのパスが与えた分（有料ラインの報酬、パス＋の10段と、その10段でだけ届いた無料ラインの報酬）を差し引く（そのシーズンが締め済みでも同じ）。
- REQ-UXS-022 商品の表示データをサーバーで作る（`GET /v1/shop/products`）：名前・タブ・中身（数量つきの行）・初回の無償上乗せの枚数（「無償コイン◯枚」、倍率の表現は使わない）・1回限りか（アカウント／クラスごと）・期間・自動更新なし・特商法／資金決済法／有償コインの使用順などの説明キーと文言。クライアントは文言を組み立てない。価格の段は docs/planning/06 §5.2。
